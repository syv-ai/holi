## D60 — The vault is a GitHub repo. There is no server.

**Context.** The rebuild was founded on two premises: that shared vaults require real-time co-editing, and that co-editing requires CRDTs over a Syv-hosted relay. Everything followed from there — Postgres as truth, Google SSO, a memberships table, a task *record* with a file projection, a server-side git mirror, snapshot history, an SSE fan-out, and a file↔CRDT bridge on every client. The premise held for the collaboration story and quietly took the rest of the product hostage: 4.7k LOC of server, and the desktop's most intricate subsystem, exist to reconcile files with a truth that isn't files. `vision2.md` withdraws the premise — **concurrent editing is deferred**, and a vault becomes what it looks like from the outside: a GitHub repo you clone.

**Decision.** Ten choices, agreed with Nicolai 2026-07-21, that stand or fall together:

1. **`apps/server` is deleted outright** — relay, Postgres, Drizzle, Google SSO, memberships, tasks table, reminder evaluator, snapshots, git mirror. v1 is a pure local Electron app talking to GitHub. Nothing needs a server: device-flow OAuth carries no client secret, and every query is a file read.
2. **Sync is auto-pull, explicit push.** Pull on an interval + on focus; your work leaves only when you **Publish**. Old Holi's failure was auto-committing and *never pulling* — the pull half is the half that was missing, and it is the half that makes a shared vault shared.
3. **Edits become local commits on idle or ⌘S.** The working tree is therefore always clean, so an incoming pull can always merge with no stash dance, a crash loses nothing, and the commit journal *is* the undo history that replaces snapshots.
4. **Pull merges, never rebases.** With ~30 autosave commits unpushed, a rebase replays each one and can conflict repeatedly on the same hunk — a failure mode manufactured entirely by autosave granularity. Merge resolves the divergence once. Non-linear history is the price, and nobody reads a vault's graph the way they read a codebase's.
5. **A conflicting merge is aborted immediately.** `git merge --abort` restores a clean tree; a banner reports the desync; **Ask Claude to reconcile** pauses autosave, re-runs the merge for real, and hands it to the agent in the drawer. The property that matters: *ignore the banner and you keep working on an unbroken vault* — the conflict never lands in a file you are typing into without your consent.
6. **The file is the task**, named `task.<name>.md`, living in the vault folder it is about. Its **path is its identity**, its **folder is its lane**, and its filename prefix is what makes it a task. This deletes the record/projection axis whole: `ProjectionStore`, version tokens, per-field patching, `RelatedRef`, `[[task:<id>]]` chips.
7. **External writes reconcile in the editor**: clean buffer reloads silently, dirty buffer takes a plain text 3-way merge, unmergeable overlap falls into the same Reconcile path as a git conflict. Needed regardless of the agent, because auto-pull can land on an open file. **Correction (2026-07-21, found during the deletion):** this was written assuming `shared/agent-merge` survived intact. It does not — its "3-way merge" forks a shadow `Y.Doc` and lets Yjs reconcile, so the merger *is* the CRDT. Only the 2-way diff survives; a conflict-reporting diff3 is new work.
8. **Reminders are evaluated locally by a tray-resident app**, with catch-up on launch. The delivered-watermark is machine-local and never committed — a fire that produced a commit is the same failure the version token was kept out of frontmatter to avoid. A reminder on a shared task notifies everyone; tasks have no assignee.
9. **GitHub is identity and access.** Device-flow OAuth, token in the OS keychain. The repo list is the vault switcher, the collaborator list is the members panel, and Holi enforces no access control of its own — if you can push, you are a member.
10. **The MCP server is deleted.** `task_list` is a glob, `task_set` is a file edit, `note_rename` becomes a vault skill in `.claude/`. Zero ops is the honest end state of "build only what Claude Code doesn't already do".

**Also settled:** clones live under a **Holi-managed root**, never an existing checkout you also use — because autosave-commit inside a tree where you keep WIP branches is destructive, and a managed clone makes that impossible by construction. **v1 keeps** daily notes (now a path check and a template), a read-only collaborators panel, and a **version-history surface over `git log`** — autosave commits are what give it material. **Google Drive is deferred**; adding an integration during the release whose purpose is removing one is how the release stops shipping.

**Why now.** The dial-back is not primarily about cost or scope — it is that the concurrency foundation had become the product's center of gravity while the things vision2 calls the product (a markdown vault, a task board, an agent that lives in it) were the parts most encumbered by it. Roughly half the codebase deletes, and the surviving half is the half you would describe to a customer.

**Rejected.** *Keep a thin server for scheduled reminders and Drive tokens* — you keep a deploy, a database and an auth seam for two features, and the ops burden survives the engine's death. *Strip Yjs but keep the server authoritative* — "truth lives on a Syv server" is precisely the model vision2 replaces. *Strangle behind the existing tRPC-over-IPC seam* — identity moves from `docId`/`vaultId` to paths, so nearly every signature changes anyway; a parallel implementation would be a rewrite pretending to be a migration, with two models alive at once. Execution is therefore **delete-first**: one commit removes the server and the CRDT stack, then main's router is rebuilt file-backed behind the seam the renderer already calls.

**Consolidated 2026-07-21** into `vision.md`, `architecture.md`, `glossary.md`, `prd/vaults-sync.md` (new, replacing `vaults-collaboration.md`), `prd/auth-identity.md`, `prd/tasks.md`, `prd/notes-editor.md`, `prd/agent.md`, `prd/daily-notes.md`, `prd/vault-apps.md`, and the phase-2 stubs. **Deleted:** `prd/server-data.md`, `prd/vaults-collaboration.md`, both `specs/`, the offline sync-hub plan, and the bridge spike.

**Verification 2026-07-25 (docs vs code).** Points 1–10 are all consolidated as prose in the living docs (`architecture.md` carries each; `glossary.md` and the PRDs carry the rest). The one docs gap has been closed: *Google Drive is deferred* was unstated and `vision.md` still framed Drive as a v1 integration — `vision.md` now moves it to *Beyond v1* with D60's own reasoning. What remains is **code that does not yet match**, and it is why this entry stays:

- **Reconcile → agent drawer (pt 5) — unbuilt.** `EditorPane.onConflict` raises only a banner (`Shell.tsx` wires it to a string); the pause-autosave → re-run-the-merge → hand-to-the-drawer path does not exist. The `pause` primitive is there (`active-vault.ts`, `sync.pause`); the drawer handoff is not.
- **Local reminder evaluator (pt 8) — landed (2026-07-31).** A tray-resident runtime sweeps every vault on a 60s tick + launch catch-up, raises native notifications, and stamps a machine-local, gitignored delivery watermark (`.holi/settings.local.json`) that never commits. Pure `sweep` behind injected seams (`main/reminders/{sweep,delivered-log,runtime,notify}.ts`), `tray.ts`, keep-alive + first-run launch-at-login in `index.ts`; the stale server-mirror types are gone. Spec/plan: `specs/2026-07-28-reminder-runtime-design.md`, `plans/2026-07-28-reminder-runtime.md`. (Native banner *display* is unverifiable under `electron-vite dev` — an unsigned-binary bundle-id collision — so confirm banners + notification-click in a packaged build.)
- **Version history over `git log` (also-settled) — landed & consolidated (2026-07-31).** The design now lives as prose in [`prd/vaults-sync.md`](prd/vaults-sync.md) §History (per-file drawer + whole-vault commit dialog, flat log, inline `@codemirror/merge` diffs, restore-as-new-commit). Build plan: `plans/2026-07-28-version-history.md`.

Residue to retire: the `[[task:<id>]]` chip grammar (`wiki-links.ts`, `wikiLinkChips.ts`) still exists, where pt 4 wanted `note_rename` shipped as a `.claude/` vault skill instead. The `mcp__holi__*` tool surface is **already gone**. The pt-7 diff3 that this entry flagged as *new work* has **landed** (`packages/shared/src/merge3.ts`, wired via `lib/editor-reload.ts`).

*This entry stays in the inbox until the code matches it — with pt 8 and version history landed (2026-07-31), the one remaining code-gap is the reconcile → agent-drawer path (pt 5) above.*

## D62 — The vault is text-first by authorship; binaries are assets it holds and emits.

**Context.** v1 shipped arbitrary-file support: any non-markdown file lives in the vault, shows in the tree with a typed icon, and opens a typed `FilePlaceholder` (`VaultSnapshot.files`, `fileKind()`). That was Nicolai's explicit ask ("obviously we need other file types"), but it landed in tension with `prd/_phase2-pdf-docx-preview.md`, which declares the vault *"text by construction"* and prescribes converting incoming PDFs/`.docx` to markdown on entry with the original archived to object storage. Two irreconcilable stances about what a binary in the vault *is* — a first-class document to render, or a source to convert-and-archive — with every downstream file surface (in-place viewers vs. an import pipeline) forking on the answer.

**Decision.** Agreed with Nicolai 2026-07-25.

1. **"Text by construction" is refined, not retired.** It is an *authoring* principle — markdown is the source of truth, and what the agent writes — not a claim that only text may exist in the vault. The working document is always markdown; the finished, sendable artifact (a client proposal) is rendered *from* it.
2. **Binary assets are allowed and persisted as ordinary committed files.** Images that markdown references, and PDFs, live in the vault as-is. There is no convert-on-entry and no forced archival of an incoming binary.
3. **Images are first-class and render.** Inline in the editor's live preview (`![](path)` and `[[path]]`), and a standalone image view replaces the typed placeholder for image kinds. This is near-term work.
4. **PDFs are outputs first.** The primary PDF path is markdown→PDF via **Typst**, delivered as a seeded **`.claude/skills/md-to-pdf` vault skill** (ported near-directly from `syv-ai/1brain`'s `.claude/skills/md-to-pdf`), agent-invokable — not an in-app feature, in keeping with D60's "ops become vault skills". Rendered or incoming PDFs may sit in the vault; **in-place PDF viewing is deferred** (open externally for now).
5. **This supersedes `_phase2-pdf-docx-preview.md`'s convert-on-entry + archive framing.** The direction is reversed — author markdown, emit PDF — and the `.docx`-import pipeline is dropped unless a concrete need reappears.
6. **Non-markdown files stay out of the link graph.** They remain out of `docs` so link-aware ops (rename, backrefs, move) are markdown-only, exactly as shipped; images and PDFs are assets referenced by path, not wiki-linkable notes.

**Also settled.** Assets are **committed straight to git for now**; **vault-size management via blob storage + reference files** (Git LFS, or a lightweight reference that renders a blob from object storage) is the deferred answer to "where binaries live at scale", revisited when vault bloat is a measured problem rather than an anticipated one. The near-term build this authorizes — inline images, a standalone image viewer, and the md→PDF Typst vault skill — gets its own spec and plan; recording this decision does not build it.

**Why.** The convert-on-entry model was written before Typst was the plan and before the daily reality was clear: Syv's rich documents are *produced* by the vault (an agent drafts markdown, then renders a branded PDF), not *imported* into it. Forcing an incoming PDF through a lossy pdf→markdown converter and hiding the original in object storage is machinery serving a direction the work does not flow in. Keeping binaries as plain committed files is the honest, zero-infrastructure default; the blob-storage escape hatch is real but is scope bought before measurement asks for it — the same discipline D60 applied to the deleted index.

**Rejected.** *Render every binary in place (retire text-by-construction).* Makes the agent blind — a PDF it cannot read is a document it cannot help with — and puts binary bloat in git with no authoring story. *Honor the PRD literally (convert incoming pdf/docx→markdown + archive).* Builds an import pipeline and an object-storage dependency for a flow that runs the other way, and archives away originals users may need intact. *Two co-equal representations of one document (binary + markdown companion, both truth).* Raises "which is truth" on every edit and sync; markdown-as-source with PDF-as-output keeps a single truth.

**Consolidates into** (once the near-term surfaces exist): `vision.md` (binaries as assets the vault emits), `prd/notes-editor.md` (inline images + image viewer), `prd/pdf-export.md` (pulled forward, vault-skill delivery), and `prd/_phase2-pdf-docx-preview.md` (rewritten or retired — the convert-on-entry framing is dead).

*This entry stays in the inbox until the code matches it.*

## D67 — Google mail/calendar rides one main-held connector; the agent reaches it via a CLI, not MCP.

**Context.** The largest deferred pillar: employees' @-account Gmail + Calendar, read and linked to tasks/notes, rebuilt natively on the Google APIs after Mailspring's death. Sign-in is GitHub (`auth-identity.md`), so there is no Google consent to ride on and no server to hold a refresh token — Google auth is a new per-user, per-machine desktop grant. The PRD stub (`prd/google-mail-calendar.md`) left five load-bearing questions open: the desktop OAuth flow, whether MCP returns (against `agent.md`'s pure-CC stance), how a link is represented, polling-vs-push, and scope/verification/multi-account. Designed whole and top-down with Nicolai 2026-08-04.

**Decision.** These stand together; full design in `specs/2026-08-04-google-mail-calendar-design.md`.

1. **Auth-code + PKCE, loopback `127.0.0.1` redirect, in Electron main** — Google's sanctioned desktop grant, built as a *sibling* of `device-flow.ts` (injectable `fetch`/`now`/`sleep`/`openBrowser`/`listen`, pure testable state machine, discriminated-union result). *Not* a reuse of the GitHub device-code flow.
2. **Main is the sole token authority.** Only main hits Google's token endpoint; `getAccessToken()` single-flights the refresh. This exists because refresh tokens *rotate on use* — two independent refreshers race and invalidate each other. A new `GoogleTokenStore`/`GoogleSession` sit beside the GitHub ones (same `safeStorage` envelope + invariants), keyed by Google `sub`.
3. **External OAuth app, reuse the existing registration.** Ship `GOOGLE_CLIENT_ID` (+ the non-confidential desktop `client_secret`) in the binary — PKCE is the protection, same reasoning `session.ts` documents for the public client id. **Single** connected account in v1; store keyed by `sub` so multi-account is additive.
4. ~~**Read-only both** (`gmail.readonly` + `calendar.readonly`)~~ — **reversed for mail 2026-08-05; see D68.** Mail is now `gmail.modify` (mark read, star, archive, trash) plus `contacts.readonly`; calendar stays read-only. Compose is still `mailto:`/deeplink, but because no compose surface is built rather than because the scope forbids one — `gmail.modify` permits sending, which is the part D68 records at length. No calendar-write. Calendar (sensitive scope) verifies lightly and ships first; Gmail (restricted, CASA) is the long pole — build in testing mode (≤100 test users), verify in parallel. This answers the scope/verification question.
5. **The agent reaches Google via a `holi-google` CLI + skill, not MCP.** The CLI proxies to a **loopback ops channel** main exposes (`{port,secret}` in a machine-local file; tokens never leave main). `holi-agent-pure-claude-code` stays intact — the PRD's "MCP returns here" prediction is *declined*. Send-gating stays recoverable via `Bash(holi-google send:*)` permission rules.
6. **A link is a plain markdown link in the file body** (not frontmatter, not a `[[wiki-link]]` — the target is an external URL, not a vault file). UI renders a chip via **render-time URL detection** (computed, not stored, like `overdue`/`pN` labels). Answers the tasks-PRD reserved question and keeps "no second representation."
7. **On-demand freshness** — fetch on open/refresh/CLI, short in-memory cache in main, nothing persisted; rely on Google's own notifications. No background poll in v1 (push is impossible with no server anyway). — **"nothing persisted" was overturned 2026-08-04; see the amendment below.**
8. **UI = workspace tabs** (agenda + mail, peers of `board`); "Connect Google" lives in **global/app settings** (account-scoped, not per-vault). Disconnect **revokes at Google + clears keychain**, independent of GitHub sign-out.

**Build order:** Connector → Calendar → Gmail → Agent skill (verification asymmetry puts Calendar before Gmail).

**Deferred:** `gmail.send`, calendar-event write, recurring-event "task lights up", background poll/in-app notifications, multi-account-at-once, disk cache/offline agenda, an MCP surface.

**Why.** Every fork resolved toward the model already load-bearing elsewhere: one process owns the token (as main owns the GitHub token), the agent uses native tools over external data (as it uses `Bash`/`Glob` over files), and a link is prose in a file (as backrefs and task links already are). The one place the PRD anticipated *new* machinery — an MCP server — is where the pure-CC stance is strongest, so it's declined; the loopback CLI gives the agent reach without a server lifecycle.

**Rejected.** *Google device flow* — not approved for the sensitive/restricted scopes; a verification dead end. *Each consumer refreshes its own token* — races on the rotating refresh token. *An MCP server* — reintroduces a server+handshake lifecycle against the held pure-CC stance; skill+CLI recovers send-gating via Bash rules. *A frontmatter link field* — the `related[]` ghost the tasks PRD killed. *Internal Workspace-only OAuth app* — erases verification but bakes "@syv.ai only" in, incompatible with reusing the existing External registration. ~~*Persist mail to disk* — contradicts "Google is source of truth".~~ **Overturned 2026-08-04, on Nicolai's call; see the amendment below.**

**Built 2026-08-04 — all four slices.** `main/google/{pkce,loopback-flow,loopback-server,token-store,session,api,calendar,gmail,ops-server,cli,electron}.ts`, a `google` sub-router, agenda + mail workspace tabs, and the seeded `gmail-calendar` skill. Three decisions were *sharpened by building them*, and each is recorded in the spec:

1. ~~**Mail is extracted as plain text, never sanitized HTML.**~~ **Overruled by Nicolai the same day, and the original design (sanitize) stands.** The build had argued that extracting text removes the XSS/tracking class *by construction* and adds no dependency. The reason that was wrong: **a mail reader that cannot render mail is not a mail reader** — the cost ("designed newsletters read plainly") was the product, not a footnote, and "we removed the feature so we would not have to secure it" is not a security win. What shipped instead:
   - **DOMPurify in the renderer** (`renderer/src/lib/mail-html.ts`), not in main — it needs a real DOM and the renderer has one, so no `jsdom`. Main hands over exactly what Google returned; there is one sanitizer, in the one process with a DOM, rather than two half-measures each assuming the other did the work.
   - **Remote content blocked by default, per-message "load images"** — the half that is easy to miss. DOMPurify stops a script; it does nothing about `<img src="https://tracker/p.gif">`, which is a read receipt fired from the user's IP on open. `src`/`poster`, `srcset`/`background`, and `url()` inside inline styles are all stripped and counted. This is what Gmail, Apple Mail and Outlook all do, so it reads as correct rather than broken.
   - **A sandboxed frame per message** (`renderer/src/lib/mail-frame.ts`), added when Nicolai asked for it the same day. Sanitized markup never enters the app's document at all, so containment is structural rather than a list of forbidden tags. `sandbox="allow-same-origin"` and **no `allow-scripts`** — granting both is the footgun that lets framed content drop its own sandbox. The frame declares its own `default-src 'none'; img-src data:; style-src 'unsafe-inline'`, which is where remote blocking stops depending on getting every attribute right (it covers `@import`, which no attribute pass can see). Written with `document.write` rather than `srcdoc`: the app needs the document anyway for height and link interception, and it is the only one of the two jsdom implements, so the behaviour is tested rather than asserted by inspection.
   - **The frame is themed.** A separate document gets no cascade, so app tokens are resolved to real values and written into its base stylesheet, `color-scheme` included. `useMailPalette` observes `documentElement` directly — a vault switch rewrites custom properties there with no React state involved — and holds object identity when nothing changed, because the palette is a frame effect dependency. The base sheet is emitted first and specificity-free, so a sender's own styling still wins inside their own page.
   - **`<style>` stays forbidden as a TAG — and since 2026-08-18 the message still gets its stylesheet.** The tag half is unchanged and not a rule that outlived its reason: DOMPurify strips stylesheet contents as an mXSS mitigation, and forcing them back with `ADD_TAGS: ['style']` measurably changes its parsing — on `<svg><style><img src=x onerror=…>` the `<img>` stops being neutralised and reaches the document as a real element. Measured, not assumed. A parser-level regression is not worth better-looking newsletters. Inline `style` attributes survive, which is how mail is actually designed. **What was wrong was the conclusion drawn from it**: that the regression made the *sheet* unacceptable, when it only made passing the sheet through the HTML parser unacceptable. `sanitizeMailHtml` now lifts every `<style>` block out of the raw markup as text before sanitizing, scrubs it as CSS (`@import` always, remote `url()` when images are blocked — counted into the same banner), and returns it as `css`; `mailFrameDocument` writes it into a `<style>` element the app built. DOMPurify's input and behaviour are untouched. This was found the long way round: MJML puts column widths in a `min-width` media query and leaves the inline width at 100% — its *mobile* fallback — so dropping the sheet rendered every multi-column mail permanently stacked, and nobody connected the two for a fortnight. One consequence worth naming: the frame's `overflow` rules moved to a third stylesheet emitted **after** the message's, because they are structural (a message that re-enables vertical scrolling becomes a scroll area inside the thread) and were previously safe only because nothing could override anything.
   - **A message carries both representations**, and the asymmetry is explicit rather than accidental: `body` (text) and `html` (raw, unsanitized). The UI renders `html`; the agent gets `body` via `textOnly()` at the ops server, because an LLM wants prose, not a table layout. `htmlToText()` survives as the text fallback and the agent's converter.
   - Links are opened with `window.holi.openExternal` from a click handler on the frame's document, never navigated — `target` is stripped, and the handler `preventDefault`s before deciding. Load-bearing rather than decorative: a sandboxed frame may navigate *itself*, so an unintercepted click would replace the message with a live web page.
   - A **narrow renderer CSP** was added alongside (`object-src`/`base-uri`/`form-action` all `'none'`), closing a standing gap: there was no CSP at all. Deliberately *not* an XSS defence — `script-src` is absent because Vite's dev preamble is inline, and a policy carrying `'unsafe-inline'` reads like protection while stopping nothing. `frame-src` is absent too: the app now renders a frame on purpose, and whether a policy blocks an `about:blank` frame is exactly the kind of thing that works in dev and fails once packaged.
2. **The ops channel moved from slice 1 to slice 4**, where its only consumer lives — a localhost server with no caller is machinery bought early. It is modelled on `agent/hook-server.ts` (ephemeral port, per-instance token, loopback only) rather than being a second bespoke transport.
3. **`holi-google` is a generated `/bin/sh` script**, not a shipped binary: no packaging entry, readable on the machine it runs on, and it re-reads `$HOLI_GOOGLE_PORT`/`$HOLI_GOOGLE_TOKEN` per invocation. Its path reaches the agent as `$HOLI_GOOGLE_BIN`, mirroring `$TYPST_BIN`; all three keys are stripped from the inherited env first, so a vault cannot redirect the agent at another mailbox.

Also landed: `tasks.create` gained an optional `description`, because create-from-event writes the link into the task **body** and silently dropping it would have defeated the representation D67 chose.

**Credentials landed 2026-08-04.** `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are now embedded in `main/google/session.ts` (supplied by Nicolai). Both are committed on purpose: a desktop client's pair is not a credential — it ships in every copy of the binary, **PKCE** is what protects the grant, and no token exists without the user completing consent in their own browser. Rotating it is a config change, not an incident. The env overrides (`HOLI_GOOGLE_CLIENT_ID`/`_SECRET`) still win.

**Live 2026-08-04.** Nicolai confirmed "the integration works" once the credentials were in — the first time this pillar has touched Google. Two corrections came straight out of using it, and both are now built: the agenda/mail chips moved to a **second row** in the sidebar (five chips made it scroll horizontally; `min-w-0` is what actually forbids that, since a flex item's default `min-width: auto` will not shrink below its text), and they are **hidden until Google is connected** — a chip whose only destination is "connect Google in settings" is a dead end wearing the clothes of a feature. Connectedness moved to `state/google.ts` with three states, because "not asked yet" must be distinguishable from "not connected" or the chips flash on launch.

**Corrected after real use, 2026-08-04 (second round).**

- **`(no subject)` on every thread** — `GoogleApi.get` sent `metadataHeaders` as one comma-joined value. Gmail read it as a single header *name*, matched nothing, and answered **200 with no headers**, so the list rendered every thread untitled from an empty sender. `get` now takes repeated query keys (array value → one parameter each). A silent-200 shape worth remembering: nothing errored, the field was just absent.
- **Mail rows gained `answered`** — the last message in the thread is one the user sent, so they are waiting on the other side. Deliberately *not* "a sent message exists somewhere in the thread", which is true forever in a long exchange and therefore says nothing about what is outstanding. Unread also got an explicit dot; weight alone was too quiet to scan.
- **The agenda showed everybody's day.** Honouring Google's `selected` was not enough — a Workspace account is subscribed to colleagues, rooms and birthdays, all `selected`, because in Google Calendar they live in separate columns. The default is now **calendars you own** (`primary` or `accessRole: 'owner'`); subscribed calendars start off and a picker in the agenda header switches them on. Overrides persist in `main/google/calendar-prefs.ts`, stored **per calendar rather than as an enabled set**, so a calendar created later follows the rule instead of arriving silently off.
- **That store lives in main on purpose:** the agent's `holi-google agenda` resolves through it too. In the renderer, switching a colleague off would have hidden them from the panel while the agent kept reading their day. Events carry **`mine`** and the calendar's Google colour; the skill tells the agent to read `mine` before describing "your" schedule, because "you have four meetings tomorrow" when three are Jane's is the failure the field exists to prevent.

**Still not verified here, and not verifiable:** no suite in this repo talks to Google. The confirmation above is a user's report of the feature working, not an enumerated check — the mail frame under a heavily-designed newsletter, and the agent's `holi-google` CLI path, are both still only exercised against fakes and jsdom.

**Amended 2026-08-04 — §7's "nothing persisted" is overturned by a bounded local cache.** Nicolai's call; built as Phase 3 of `plans/2026-08-04-google-pillar-depth.md`. §7 and the *"Persist mail to disk"* rejection above are both struck.

**What changed, and why it does not contradict "Google is the source of truth".** A bounded last-N cache is not a mirror. It holds the last 500 threads for the questions actually asked, in `userData/google-cache.db`; anything past that tail is a request, and every read is checked against the connected account first. Google still decides what is true — the cache decides only what is painted before Google answers.

**The number that justified it.** A mail refresh was `threads.list` plus one `threads.get` per thread — **26 requests for 25 threads**, nearly all re-downloading mail that had not changed. With `history.list` deltas on top of the cache, an unchanged refresh costs **one**.

Four properties carry it, and each exists because the obvious alternative is worse:

- **`node:sqlite`, not a native module.** Built into Node 24 / Electron 43, so there is no `electron-rebuild` step and no compiled dependency in the packaging story. This is the only reason a database was affordable here at all.
- **The database is unencrypted, on purpose.** SQLCipher is a native module — precisely what `node:sqlite` was chosen to avoid — and hand-encrypting columns would foreclose the FTS5 search the schema is shaped for. The protection is the OS account and full-disk encryption, which is what every desktop mail client relies on and what already protects the vault's own notes sitting beside it.
- **It is in `userData`, not in a vault.** Mail is *account* data and a vault is a shared git repo: caching a client's inbox there would push it to teammates on the next sync. (Nicolai proposed per-vault; this is why it is not.)
- **Account scope and disconnect are structural.** `useAccount(sub)` wipes everything when a different account connects, before any read can happen. Disconnect deletes the **file** (and the `-wal`/`-shm` sidecars), not the rows — emptying tables would leave recoverable mail on a disk the button had just promised was clean. Both hang off `googleSession.onChange` rather than off the disconnect procedure, because `onChange` also fires for a **dead grant**, and a revoked connection is just as much "this is no longer yours to hold".

**The agent is deliberately outside all of it.** `createGoogleOpsServer` is handed `listAgenda`/`listThreads` — functions that take no cache parameter and therefore *cannot* read one. D67's "the agent asks for current data" is enforced by the types rather than by remembering it while editing `main/index.ts`.

**Calendar gets no incremental sync, and that is a refusal rather than an omission.** `events.list`'s `syncToken` **cannot be combined with `timeMin`/`timeMax`** — Google's own reference lists both among the parameters that "cannot be specified together with `nextSyncToken`", alongside `iCalUID`, `orderBy`, `q` and `updatedMin`; an expired token returns 410. So an incrementally-synced agenda would mean mirroring **every event at every date, per calendar**, to serve a view that shows seven days. Refused. Calendar gets a cache for *paint* only: a separate `agendaCached` procedure the panel draws immediately and replaces the moment the live fetch lands. Two procedures rather than one stale-while-revalidate answer, because there is no push channel to tell the renderer the second one arrived. **Do not re-derive this** — quoted from the docs rather than recalled.

**One contract was corrected while building.** The plan specified a single mailbox-wide `historyId()`. That is wrong: Gmail's cursor is mailbox-wide but each cached list is written at a different moment, so one shared cursor asks "what changed since 200?" against a list last written at 100 and silently loses everything between. `GoogleCache.historyId` takes the list key. Found by a test written after the first ten passed.

**Consolidates into** `prd/google-mail-calendar.md` (the five open questions became settled prose — done), and `prd/agent.md` (§Tool surface: the CLI surface for external data, and that the "MCP returns here" prediction was **declined**), `prd/tasks.md` (§Deferred: linking resolved to a body link), `prd/auth-identity.md` (the second, independent OAuth provider). **Consolidated 2026-08-05** into all three, together with D68–D70 — see below.

## D68 — Mail is read-write within a bounded set. Calendar stays read-only.

**Context.** Nicolai, from real use: *"opening an unread email doesn't mark it read."* It read as a missing call and was not one. Three facts, verified in the source before anything was built: `GOOGLE_SCOPES` was `gmail.readonly`, which cannot remove the `UNREAD` label; `GoogleApi` exposed only `get`/`getAll`, so **nothing in the app could write to Google at all**; and read-only was asserted as *intent* in three places — D67 §4, the scope comment in `session.ts`, and the module note in `MailView.tsx` ("pretending otherwise would be a button that cannot work"). So the ask was a scope change, a fresh consent screen and an amendment to a numbered decision, not a fix. Put to Nicolai as a choice between mark-read alone, the full triage surface, and leaving it read-only; he chose the full surface, and separately approved adding contacts to the same consent screen rather than paying for a second one later.

**Decision.** Six parts.

1. **`gmail.modify` replaces `gmail.readonly`.** It is a superset, so requesting both is redundant. Calendar is untouched and stays `calendar.readonly` — nothing asked for calendar writes and D67's deferral of them stands.
2. **Four writes, and that is the whole surface:** mark read (on open, and only when the thread is actually unread), star, archive, trash. No label editing. No compose.
3. **`contacts.readonly` rode the same consent screen**, which is the only reason it is in a mail decision. It puts a real address book behind `@`-completion, merged *behind* the local sender corpus rather than replacing it — see §Ranking below.
4. **Local patch is optimism; `history.list` is truth.** Gmail records this app's own label changes in the mailbox history, so the next `syncThreads` reconciles every cached list independently of what was patched. That is what licenses archive/trash simply dropping the thread from *every* cached list, including a search that might still legitimately match: the next sync restores it. This is a cache, not a mirror.
5. **The two processes take opposite orders, deliberately.** The renderer paints first and reverts on refusal — a revert costs a re-render and nothing is persisted. `main` calls Google first and touches the cache only on success, because a cached write Google refused is the one divergence a delta sync can never repair: history reports what changed *at Gmail*, and for a refused request nothing did, so no event exists to correct it and the wrong value survives every restart.
6. **The agent gets none of it.** `createGoogleOpsServer` is handed read functions and never `googleData`, so the exclusion stays structural rather than remembered.

**Which half of the boundary Google actually enforces — the uncomfortable part.**

- *Permanent delete is impossible.* It needs `https://mail.google.com/`, which is not requested and will not be. Trash is Gmail's trash, recoverable for 30 days, which is why the button says trash and not delete.
- *Sending is merely unbuilt.* **`gmail.modify` permits `users.messages.send`**, and no lesser scope grants `threads.modify` — so archive cannot be bought without also buying send. "Holi cannot send" stopped being a fact about the grant the moment this landed and became a fact about the code: there is no function that sends. This matters to D67 §5, which gated the agent's future send behind `Bash(holi-google send:*)` permission rules *while treating the read-only scope as the outer wall*. That wall is gone; the permission rule is now the only one rather than the second. Accepted — archive is unobtainable otherwise — but recorded, because a defence that quietly became single-layered is exactly what nobody re-derives later. **Sending, when it is built, needs no new scope and no second consent screen.**

**Verification is unchanged, and this is worth stating so nobody re-derives it.** `gmail.modify` is *restricted* — the same CASA tier `gmail.readonly` already sat in — so D67's testing-mode posture (≤100 test users, verification in parallel) carries over untouched. `contacts.readonly` is *sensitive*, the lighter tier. Neither is a new verification problem. GCP-side this cost exactly two changes: enabling the People API, and listing the two scopes on the consent screen.

**A class of bug worth naming: a stored grant that predates the scopes.** `StoredGoogleAuth.scopes` had been written on every connect since the connector landed — the comment even said "so a failure can name the missing scope" — and read by nothing. Widening `GOOGLE_SCOPES` does **not** invalidate an existing grant: the refresh token goes on minting tokens for the old scopes, mail still lists, and only the new calls 403. The user's evidence says Google works, so the symptom reads as a broken feature and no amount of retrying fixes it. `GoogleSession.missingScopes()` compares the two and vault settings offers Reconnect. The general shape — *a capability widened in code while the credential still reflects the old one* — will recur with any future scope change.

**Ranking, for `@`-completion.** Senders across loaded threads carry a frequency count; contacts arrive at zero and sit behind them. The local corpus is deliberately **not** replaced: it is what keeps completion working when the contacts request is cold, refused, or the grant predates the scope — and in the common case "who actually writes to you" is the better answer anyway.

**Why.** Every part resolved toward a rule already load-bearing here. One process owns the token, so one process owns the write. The cache is a cache, so a wrong entry is a performance problem and not a correctness one — which is what makes optimism affordable in the renderer and unaffordable on disk. And the agent stays on native tools over data it re-reads, so it does not get a mutation surface merely because one now exists.

**Rejected.** *Mark-read alone* — the same consent screen and the same CASA tier buys the whole triage surface; splitting it across two re-consents spends the user's attention twice for nothing. *Leaving it read-only and being honest about it* — offered, and declined: the bold state is what an inbox is scanned by, and a reader that never clears it makes the list wrong for everyone who uses both Holi and Gmail. *Optimistic cache writes in main* — the one divergence no later sync can find. *Patching only the visible list* — two views disagreeing with neither obviously wrong. *A `TRASH` label via `modify`* — answers 200 and trashes nothing, which is why trash has its own endpoint and its own test asserting the body carries no such label. *Giving the agent the writes* — a separate decision nobody has taken.

**Built 2026-08-05**, eight commits (`b89f42e`…`b9d3a81`). Suites: node 995, dom 182, shared 229. **Nothing here has touched Google** — no suite in this repo does, so every write is verified against fakes. Real-mailbox behaviour of `threads.modify`, `threads.trash`, the `labelId: 'INBOX'` history assumption in `mail-sync.ts`, and the People API response shape are all unproven until it is used.

## D69 — A cached list is defined by every filter that narrows it; a thread that leaves the inbox leaves the list; mail renders on paper.

**Context.** A review of the D68 branch, plus three reports from real use: "Load images" not sticking, rich mail rendering black-on-dark, and no counts on the category tabs. The review found two defects that green suites sat on top of, both confirmed by running the real modules rather than by reading them.

**Decision.** Six parts. The first three are corrections; the last three are the surface they exposed.

1. **A departure is not a deletion, and not a refetch.** `history.list` reports archive as `labelsRemoved: ['INBOX']` and trash as `labelsAdded: ['TRASH']`. Neither is `messagesDeleted`, which was the only thing that took a thread out of a cached list — so the thread was refetched (`threads.get` still answers; it is in All Mail), found absent from the cached list, and re-added by `merge` as **new mail, at the top**. It then stuck: the merged list was written back and the cursor advanced, so no later delta mentioned it again. `readHistory` now has a third bucket, `left`, applied in `merge` to the *added* branch as well as the kept one — filtering only the latter is precisely what let it through. Both directions are handled (`INBOX` added is an un-archive), and for an explicit **search** a departure degrades to a refetch, because a search may still legitimately match an archived thread.
2. **`cacheKey` carries every option that narrows the list.** It was `query|category` while `unread` also composes into the Gmail query. The two lists shared one entry, and the failure was not staleness but a wrong answer in both directions: a warm cache served the whole inbox for "unread only", and a cold unread-only fetch wrote its narrower answer under the plain inbox's key. `SHAPE_VERSION` is bumped to `3` — not a type change, but the only way keys written under the old scheme ever leave the disk.
3. **`otherContacts` was never reachable, twice over.** `otherContacts.list` takes **`readMask`**, not `connections.list`'s `personFields`, and is covered by **`contacts.other.readonly`**, not `contacts.readonly`. Both failures are 4xx, both were swallowed by `listContacts`'s deliberate `[]` policy, and the result was an address book that answered successfully and was empty for exactly the people it was built for. The scope is added — approved in the knowledge that it costs one more re-consent. The test's fake answered on URL alone, which is why it could not have caught either half; it now refuses the way Google does.
4. **Mail renders on paper unless it brings no design of its own.** Mail declares its ink (`color: #333`) and inherits its paper, because for thirty years the client's paper has been white. The frame always took the app's theme, so a dark theme rendered a great deal of real mail black-on-black — and the images with it, since a logo is usually dark ink on transparency. `bringsOwnDesign` decides, and is deliberately asymmetric: any colour, `bgcolor`, `<font>` or `<img>` means paper. Wrongly giving paper costs a white block in a dark app, which is what every other mail client shows; wrongly giving the theme costs an unreadable message. Read from the **raw** HTML, so pressing "Load images" cannot flip the canvas underneath a message.
5. **Two remote-content permissions, with two lifetimes.** "Load images" is this message, held in renderer state for the session — it was held in the *component*, and the reader unmounts on every thread close, which is why it did not survive coming back. "Always from this sender" is persisted in `userData` and applies forever. Offering only the first makes the user re-decide the same newsletter weekly; offering only the second turns a one-off peek into a standing disclosure. Settings shows the count and can forget them all, because a permission that cannot be seen is not one that can be withdrawn.
6. **Category counts are counted, not estimated.** The picker showed none because the obvious source is `resultSizeEstimate`. The exact-looking alternative, `labels.get` on `CATEGORY_PROMOTIONS`, counts the **whole mailbox** including archived mail — a gap this app now widens, since it can archive without reading. So each tab is `threads.list` scoped `in:inbox category:x is:unread`, ids only, counted; `500+` past one page. Five requests, spent only when the picker is opened.

**Also corrected, from the same review.** `GoogleApiError.code` now crosses the IPC seam as a tRPC code (`FORBIDDEN`/`TOO_MANY_REQUESTS`/`UNAUTHORIZED`) rather than leaving the renderer to regex Google's prose — `ipc-link.ts` already records this codebase learning that lesson once. The optimistic undo in `MailView` is guarded by a generation counter, because restoring a wholesale snapshot after the list has moved on discards a concurrent write or a landed refresh; when it has moved, the recovery is to re-read rather than to invent an undo. `PATCHABLE_LABELS` is derived from the label→flag table instead of being a second declaration that has to agree with it. The address book is held per connected account in `googleData`, where it was refetched on every `MailView` mount. `GoogleApi.post` returns `void`, since no caller ever read the `T | null`.

**Why.** Two of these share a root: **a cache entry is an answer to a question, and the question has to be written down completely** — `cacheKey` omitted a filter, and `merge` omitted a way for a thread to leave. Both produced a confidently wrong list rather than a stale one, which is the failure mode a cache is supposed to have made impossible. The rendering half shares a different root: the app's theme is a fact about the app, and a message is not the app.

**The lesson the review was run on, and which it confirmed.** *A test that asserts what the code assumes, rather than what the external system does, passes while the feature is broken.* It had already happened once in D68 (`missingScopes` seeded with the request form of the scopes). It had happened again in the People fake, twice, in a file written the same day. Nothing in this repo talks to Google — every response shape is a fake written from documentation — so this is the standing failure mode of the whole pillar, not an incident.

**Rejected.** *Renumbering `position` on drop* — checked and genuinely unnecessary; `readThreads` only orders by it and `writeThreads` deletes by key before reinserting from zero. *Dropping `otherContacts` rather than adding a scope* — offered, and declined: for a Workspace account it is most of the address book. *Inverting every write to undo it precisely* — "unarchive" is not expressible, so the snapshot stays, guarded. *Per-sender only, or per-message only, for images* — the two answer different questions. *`labels.get` for tab counts* — one request instead of five, and the wrong number.

**Built 2026-08-05.** Suites: node 1013+, dom 205, shared 229, typecheck 0, eslint 0 errors. **Still nothing here talks to Google** — true on the day, and **superseded**: by 2026-08-14 mail read, the four triage writes and the calendar agenda had all run against a real account. See `prd/google-mail-calendar.md` for what is proven and what is not; that is the live list, and this line is a record of a moment. The `readMask`/`contacts.other.readonly` fix, the departure handling against a real mailbox, and whether `history.list` scoped to `labelId: 'INBOX'` reports an `INBOX` removal at all are unproven until used — note that if it does *not* report it, part 1 is inert for this app's own writes and the remaining exposure is an archive done in Gmail's web UI never leaving Holi's cached list.

## D70 — The agent may do anything the user can undo, and nothing that reaches another human.

**Context.** D68 §6 gave the agent none of the mail writes it had just built, and said why in one sentence: *"giving an LLM archive and trash over a real mailbox is a decision nobody has taken."* Nicolai asked for it — mail CRUD plus calendar — and answered the shape of it in two notes rather than by picking an option: **send is in, but "gated hook on sending emails, should always ask, tap into the hook system, don't build a hack for this"**, and calendar is *"mostly read, write from time to time — the user could ask the agent to plan out tasks for the day, and the agent could slot them in."* He separately chose a wall whose outer layer survives a user clicking Allow-always. Those two answers look contradictory (one builds `send`, the other's layer 1 was "no irreversible op exists") and are not: a hook returning `ask` **overrides `permissions.allow` and overrides a prior "don't ask again"**, which is exactly the undefeatable-by-one-click property that was being asked for. The hook *is* the structural layer.

**Decision.** Designed in full in `docs/specs/2026-08-05-agent-google-writes-design.md`. The parts that are law:

1. **The line is reversibility, not write-ness.** Three tiers with three *different* enforcement mechanisms, deliberately — one mechanism at three strengths is one edit away from being one mechanism at one strength. *Impossible* (permanent delete) stays enforced by the scope Google was never asked for. *Reaches a human* (`send`, `reply`) is a `PreToolUse` hook that always asks. *Undoable* (mark-read, star, archive, trash, draft, and the calendar writes) is seeded `permissions.ask`. What matters to the user is not whether the agent changed something; it is whether they can put it back.
2. **Attendees are the calendar's version of send.** `events.insert` carrying attendees emails them; deleting such an event emails cancellations. Time-blocking needs none of that, so **main refuses attendee-bearing events to the agent structurally** — in the function it is handed, not as a rule in `SKILL.md` the agent could reason around. This keeps calendar write inside the undoable tier and means the hook only ever guards mail.
3. **The D68 §6 exclusion widens rather than dissolves.** `googleData` already exposes the four writes as bound methods that call Google then patch the cache, so the ops server is handed **more functions and still never `googleData`**. Because the agent calls the identical function the router calls, there is no stale-until-next-sync window and no second cache path — which answers the open question of where agent writes should come from without weakening anything.
4. **One new scope, `calendar.events`** — *sensitive*, the same tier as `calendar.readonly`, so no new verification burden and a consent-screen edit GCP-side. Mail needs nothing: `gmail.modify` already permits `messages.send` and `drafts.*`, which is D68's uncomfortable part being spent on purpose rather than by accident. Everything lands together; **consent is given once, at the end** (Nicolai's instruction, over a phased build that would have spent his attention three times).

**The gate D67 §5 specified could never have fired, and that is the finding here.** It named `Bash(holi-google send:*)`. `SKILL.md` tells the agent to invoke `"$HOLI_GOOGLE_BIN" send`, so the literal command text contains no `holi-google` at all — the rule would have matched nothing, forever, while reading in the ledger as a gate. The fix is to make the command text predictable rather than to write a cleverer pattern: the generated `bin/` goes on the agent's `PATH`, the skill uses the bare name, and the hook's `if` covers both spellings. **The general shape — *a gate specified against a command string nobody checked against the invocation* — is worth carrying: it fails open, silently, and it reads as protection.**

**The honest limit, recorded because nobody re-derives it.** This gates a *cooperative* agent, not an adversarial one; no string match survives `eval`, a variable, or `sh -c`. The supported claim is **"the agent never sends without you seeing it"**, not "the agent cannot send".

**Why.** Reversibility is the only cut that sorts these operations without a judgement call, and it happens to be the cut the user experiences. Everything else followed from refusing to let a bound live somewhere the bounded thing can read it — which is the same reason D68 handed over functions instead of an object.

**Rejected.** *Withholding `send`* — recommended, and declined: an agent that drafts but never sends makes the user the transport layer for its own output. *A main-side confirmation dialog* — the strongest wall, declined as bespoke machinery where a supported mechanism already has the property it was wanted for. *`permissions.ask` alone for send* — one "don't ask again", six weeks before the send that mattered; D68 §6's "a defence that quietly became single-layered" arriving on schedule. *A skill rule forbidding attendees* — the agent is the thing being bounded. *Bodies as command arguments* — quoting accidents, and it puts the whole email into the confirmation prompt's text.

**Built 2026-08-05**, twelve commits (`62ccd89`…`21ba457`) over the plan in `docs/plans/2026-08-05-agent-google-writes.md`. Suites: node **1097**, dom **207**, shared **229**, typecheck 0, eslint 0 errors.

**Two departures from the plan, both forced by what the code turned out to be.**

1. *The ops-server widening and its wiring are one commit, not two.* `GoogleOps` going from 3 methods to 12 means `main/index.ts` must satisfy it in the same change or the tree does not typecheck; splitting them would have committed a knowingly broken intermediate.
2. *The gate carries no `if` condition.* The plan proposed `if: "Bash(holi-google send:*)"` as the declarative form. It matches one of the **three** spellings the agent can produce (the bare name via `PATH`, `$HOLI_GOOGLE_BIN`, an absolute path), and a condition that misses one fails **open** while still reading like protection — which is the exact mistake D67 §5 already made. The hook therefore matches `Bash` broadly and decides in the script, at the cost of one child process per Bash call.

**Found while building, each by a test rather than by reading.** `postJson` had to be its own function rather than a flag on `post`, because the two want opposite things from an unreadable 2xx. A `reschedule` that built its curl arguments with `set --` while still looping over `$@` read its own output. The obvious bound on request-body size — destroy the socket at the limit — kills the connection before the 413 can be written, so the caller learns nothing; discarding while continuing to drain bounds memory just as well and still answers. And `undefined` already meant "no such route" in the ops server, so a `Promise<void>` operation needed a sentinel or every successful archive would have 404'd.

**A test-harness bug worth recording, because it wears the costume of a product bug.** `execFile` has no `input` option — that belongs to the `*Sync` variants — so passing one silently does nothing, the child's stdin never closes, and `curl` blocks on `@-` until the runner gives up. It presented as "the CLI hangs on send". The run went from 63 seconds to 4 once the helper spawned properly.

**Amended the same day, from a review of what had just been built — both about the same gap: *the user is asked to approve a send they cannot see.***

- *A reply defaulted to reply-all.* It copied the thread's `Cc`, so one instruction reached everyone on a six-person thread — on the single operation that reaches people at all, and the one whose recipients are *derived* and therefore absent from the command being approved. Now sender-only; `--all` makes the widening explicit. A default that silently widens an audience nobody can check is the wrong default.
- *The prompt said only "this sends mail".* It is the entire consent surface, and consent to send means knowing to whom. The gate now reads `--to`/`--cc` out of the command and names them. For a `reply` it says plainly that Holi derives the recipients and they are not visible here — an honest gap beats a reassuring sentence that implies otherwise. It also states that the message text is on stdin and is not shown, which is why `SKILL.md` now requires the agent to say what it is about to send, in chat, first.

**The gate did not exist in any vault that already existed, and that was found by looking rather than by testing.** Two independent reasons, both of which had to be fixed for D70 to be delivered at all:

1. *`ensureSeeded` is write-if-absent.* Every established vault already has a `.claude/settings.json`, so it is never updated — the gate would have arrived as a hook *file* with nothing invoking it.
2. *`vaults.open` never called `ensureSeeded`.* Only the clone/adopt path did, so an existing vault re-seeds never. The function's own doc had always said it was "safe to run on every vault activation"; the call site never honoured it.

Together they meant `send` reaching a real mailbox with **no gate and no permission rule** — not unverified, absent. It is D68's stale-grant shape exactly: *a capability widened in code while the stored artifact still reflects the old one.* Fixed by merging `settings.json` key-wise (the way `.gitignore` was already merged line-wise: add what Holi requires, keep the user's own hooks and rules, `null` when there is nothing to do, and leave malformed JSON alone rather than overwrite it), and by seeding on open. **The generalisation worth keeping: a seed that only runs at creation is a migration that never happens.**

Pre-seeding the router test rig changed seven tests that had been asserting against a vault carrying no managed files — an arrangement that cannot exist in reality, which is why they were asserting exact document lists at all.

**Verified against a real account, 2026-08-14** — the manual pass this entry had been waiting for, run as task 0 of the D71 plan. The agent drafted, sent, and replied to a live thread from a real vault, and the received message's raw source was read rather than trusted. What that settles:

- **Reply threading works, and the headers are exactly the contract.** The delivered reply carries `References: <first> <second>` — the whole chain, oldest first — with `In-Reply-To` set to the last of them. This is the assertion the entry above called "the whole property": with `In-Reply-To` alone the send succeeds, returns an id, and lands as a new conversation, and nothing in the response says so. It threaded.
- **`buildRfc822`, `messages.send` and `drafts.create` are real.** A draft appeared in Gmail Drafts addressed correctly; a send arrived.
- **The gate fires — and by a stronger mechanism than the one designed for.** The test specified was *allow, click "don't ask again", send again, the prompt must reappear*. **There is no "don't ask again" affordance on a hook-driven `ask` at all**, so the opt-out this design was built to survive cannot be reached in the first place. The property holds structurally rather than by defeating an opt-out. Recorded as an observation of the prompt Claude Code renders, not as a proof that no other path could ever allow-always. **This says the gate fires when it is reached; it does not say every send reaches it.** Ten days later the agent sent through a claude.ai Gmail connector and the gate never saw the call at all — a `Bash` matcher cannot match an MCP tool. **D72 is the fix**, and the paragraph above should be read as being about the `Bash` path only.
- **A charset assumption became a measurement.** `buildRfc822` declares `8bit` on the reasoning that the transport is Gmail's own API rather than an SMTP hop that might be 7-bit. Gmail **re-encodes to `quoted-printable` on delivery** (`=E2=80=94` for an em-dash) and the character arrives intact, so the declaration is honoured semantically and normalised for transport. The comment in `mime.ts` was right for the right reason; it is now known rather than argued.

**A wart the pass found, which no test would have — and the fix, taken the same day.** `holi-google draft` followed by `holi-google send` produced **two messages**: `send` composed a fresh one rather than sending the draft, so the draft was orphaned in Drafts beside a sent copy. The two subcommands had no link between them, and the agent used them exactly as documented.

`send --draft <draftId>` closes it. `GoogleOps.send` now takes *either* a composed mail or a draft id, and the draft form routes to `drafts.send` — the same call D71's composer uses, and for the same reason: Gmail deletes the draft as it sends, which is the only way "draft it, then send it" ends with one message. **They are alternatives, not a merge**: a draft already carries its recipients, subject and threading headers, and taking half from each is how a send goes somewhere nobody chose, so a `draftId` wins outright and any composed fields alongside it are ignored.

Three things it needed beyond the route:

- **`--draft` must not read stdin.** Every other send form ends in `--data-urlencode body@-`, which blocks forever on a command nobody piped into. The failure would have been a hang, not a wrong message, and a test asserts the command completes.
- **The gate still asks, and says something true.** A draft send reaches a human like any other. Its recipients are in the draft rather than in the command, so the prompt says so — the same honesty `reply` already needed. The generic "Holi could not read the recipients, so check the command" would have been a lie here: nothing failed to parse, and the command does not contain the answer.
- **`SKILL.md` taught the broken loop.** It said *prefer `draft`*, and gave no way to then send the thing drafted. It now says to keep the id `draft` returns, and that composing a second time delivers one message and orphans another.

**Still unproven:** `postJson`'s unreadable-2xx path, the three `events.*` shapes, and **`drafts.create` with a `threadId`** — the draft written during the pass was a new message, so a draft *filed into a thread* has still never been made against a real mailbox.

**Consolidates into (D67–D70, done 2026-08-05).** `prd/google-mail-calendar.md` — no longer a stub: built-and-live status, the read-write goal set, the attendee bound, the cache-not-mirror non-goal, the superseded scope line, the declined MCP prediction, and the pillar's standing failure mode. `prd/agent.md` §Tool surface — the twelve-subcommand surface, and **the read-only bullet deleted**: it claimed the agent could not send "not by policy, but because no such scope exists", which was false in every clause and was the third file this week carrying that stale invariant. §Permissions gains the send gate as the one piece of machinery among the configuration, why it is a hook rather than a rule, why it matches `Bash` broadly, and the seed-on-open rule. `prd/auth-identity.md` — the scope row, and the scope-widening trap that has now bitten twice. *The living docs are law again; these four numbers survive only in code comments and git history.*

## D72 — A vault agent inherits the vault, not the machine.

**Context.** Asked to draft an email, the vault agent used a **claude.ai Gmail connector** rather than `holi-google`. Not a malfunction — it reached for the more convenient of two tools it could see, which is what it should do. The problem is that it could see it at all. That one call routed around D67 (main is the sole token authority), D68 (Holi's writes patch Holi's cache) and D70 (`send` passes a gate that always asks) — the last because the gate matches `Bash`, and an MCP tool call is not a shell command, so it **deferred**. D70's recorded limit was *"this gates a cooperative agent, not an adversarial one"*; this is worse than that admits, because a cooperative agent walked around it without trying. It could have *sent* with no prompt.

**The connector is a symptom.** A vault agent is a plain Claude Code session run in the vault's directory, so it inherits the whole of the user's `~/.claude`: skills (`find-skills`, `humanize-text`, `pr-review`, `web-artifacts-builder`), every installed plugin and marketplace, an `azure-devops` MCP server, and `skipDangerousModePermissionPrompt: true`. Nothing distinguished "the vault's config" from "this machine's config", and the agent got the union.

**Decision.** Designed in full in `docs/specs/2026-08-14-vault-agent-config-isolation-design.md`. The parts that are law:

1. **A vault agent's config directory is Holi's, not the user's.** `CLAUDE_CONFIG_DIR` points at `userData/agent-config/`, so home skills, plugins, marketplaces and MCP servers are excluded *by construction* rather than by a list of things to disable — a list would need extending every time Claude Code grows a new kind of user-level content, and would fail open when it wasn't.
2. **One shared directory, not one per vault.** Isolation costs a `/login` per config directory (§3 of the spec — measured, not assumed), and per-vault directories would charge that per vault. They buy separate settings, which nothing needs. **Per-vault session history comes free anyway**, because Claude Code keys transcripts by working directory: one shared directory still gives each vault its own `--resume`.
3. **Isolation is from the machine, not from the vault.** The vault's own `.claude/` is untouched and still outranks everything, and `--strict-mcp-config` stays off, because a vault is entitled to declare its own MCP servers and skills. What is being removed is the accident of whose laptop it is running on.
4. **Holi does not report the logged-out state at all.** *(Revised in build — the law first read "read it from a file, never from the terminal", on the standing decision against inferring Claude Code's state by parsing its output. That was the right answer to the wrong question; see the build notes below.)* Claude Code prints `Not logged in · Please run /login` in the terminal the drawer is already showing, and `/login` is typed into that same terminal, so **the terminal is both the notice and the fix**. Holi keeps no copy.

**The measurement that shaped it, and the inference it killed.** There is no `~/.claude/.credentials.json` on macOS; credentials are in the Keychain. From that it *looks* as though relocating the config dir leaves authentication alone. It does not — a fresh `CLAUDE_CONFIG_DIR` reports `Not logged in`, and symlinking `~/.claude.json` back does not fix it. Credentials are keyed to the directory rather than stored beside it. **The plausible inference was wrong and a ninety-second experiment caught it** — the same shape as this pillar's standing failure mode, arriving in a new pillar.

**Half shipped the same day** (`438ca2a`), because it was severable and free: `disableClaudeAiConnectors: true` in the seeded vault settings (settable in any scope, and `true` in any source wins, so a checked-in project file settles it), plus the send gate extended to match `mcp__.*[Gg]mail.*` and ask on send/reply/forward — belt to the setting's braces, for a vault whose settings regress. It defers on connector drafts and reads: this gates what cannot be undone, not what it dislikes. **Both go through the merge path**, since every vault that exists already has a `settings.json` and a creation-only change would have reached none of them — D70's own lesson applied to itself.

**Rejected.** *Per-vault config directories* — a login per vault for separate settings nothing needs (law 2). *Symlinking `~/.claude.json` to keep the login* — tried; does not work, and would drag the machine's MCP and project state back in. *Settings-only, no relocation* — closes the connector hole and nothing else, because project settings cannot reach user-level skills or plugins; shipped as far as it goes, and it is not the general fix. *Copying session transcripts into the new directory* — rewriting another program's internal state store to save one empty `--resume`. *Detecting the logged-out state by parsing the terminal* — against a standing decision, and unnecessary. *Reporting the logged-out state **at all*** — added in build, removed in build: the terminal already says it, and any Holi-side copy needs a refresh event that `/login` does not produce.

**Open, and deliberately not decided.** Whether anything from home deserves an allowlist: `syv-skills` (`hjernen`, `tilbud`) is a home *plugin* and will disappear from vault agents. That may be right — a vault agent is for the vault — or it may be missed within a week. The escape hatch is a symlink into the shared config dir, and the call should be made when it is felt. Separately: whether a vault agent should share the user's Claude login at all is a question about identity, not about config directories.

**Built 2026-08-14** (laws 1, 2 and 4; the connector half had shipped that morning). Three commits, and the plan's five tasks collapsed to three once the code was read:

- **`buildAgentEnv` gains `configDir` → `CLAUDE_CONFIG_DIR`**, and strips any inherited value first, beside the `HOLI_*` keys and for a stronger version of their reason: a spoofed hook port sends a hook somewhere wrong, while a spoofed config dir returns the agent to the machine config this decision exists to exclude. `buildAgentArgs` was not touched — `--strict-mcp-config` stays off (law 3).
- **`agent-config-dir.ts`** provisions `userData/agent-config/` on **every app launch**, not at first run, and merges `disableClaudeAiConnectors: true` key-wise rather than rewriting the file — the directory accumulates the user's own choices (their `/login`, a model preference) and a wholesale rewrite each launch would discard them. It is a *separate* required set from the vault's, so it is not `settingsWithRequired`: the vault's carries hook commands whose paths are relative to a vault and mean nothing at user scope. `projects/`, `sessions/` and `.claude.json` are left to Claude Code — pre-creating them is guessing at another program's schema.
- **The login notice was deleted, and getting there took two wrong answers.** The plan's third task specified a new "needs a login" line in `AgentPanel`. The panel **already had one**, wired to `AgentStatus.authenticated` ← `isClaudeAuthenticated()` **against the machine's home** — so the defect was the reverse of a missing feature: after laws 1–2 that probe reads the wrong directory and reports a login the relocated agent does not have. Wrong answer one: point the probe at the config dir. Then the first real run showed the notice **staying up after a successful `/login`**, because `/login` spawns nothing, opens no turn and exits nothing and so fires none of the three events that push status. Wrong answer two: watch the config directory and disarm on the flip — built, tested, and **rejected on sight by Nicolai as complexity in service of a redundant string.** *"Claude Code requests a login in the content below."*

  It does, in the same terminal, three lines under the header — and `/login` is typed into that terminal too. **The header line was a second copy of state Holi does not own**, and every fix considered was machinery for keeping a copy honest. Deleted: the notice, `AgentStatus.authenticated`, and `isClaudeAuthenticated` with its tests. **The general lesson is the one worth keeping: a mirror of another program's state needs an event to refresh on, and when there is no such event the answer is to stop mirroring, not to go looking for one.** Two rounds of increasingly clever refresh went by before anyone asked whether the string needed to exist.

**Suite after: node 1217 (was 1199), dom 337, shared 229, typecheck clean, 0 eslint errors.** No renderer test was written — nothing about any of this ended up in the renderer except a deletion.

**Consolidates into `prd/agent.md`** — §Config layering (the personal layer is no longer "the user's `~/.claude`"; it is Holi's directory, with the cost, the loss and the vault's continued authority stated), §Runtime (the `CLAUDE_CONFIG_DIR` spawn line, which said the exact opposite), §Auth (there is no probe: the terminal is both the notice and the fix), §Tool surface (that "there is no MCP server" was a claim about what Holi *declares* and only now describes what the agent can *reach*), §Permissions (the gate's `Bash`-only blind spot, and that enumerating how a capability is reached is only as good as the last tool inventory) — and `architecture.md` §Config layering. **Planned in `docs/plans/2026-08-14-vault-agent-config-isolation.md`.
