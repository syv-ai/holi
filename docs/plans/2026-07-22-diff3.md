# diff3 Implementation Plan

> **For agentic workers:** Use the executing-plans skill to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `packages/shared/src/merge3.ts` — a 3-way text merge that **reports conflicts rather than resolving them**, so an external write landing on a dirty editor buffer either merges cleanly or routes to the same reconcile path a git conflict uses.

**Architecture:** One file, two layers. A **line diff** built on `fast-diff` (already a dependency, currently unused) via the standard line-to-codepoint mapping, and a **diff3 walk** over the two resulting hunk lists. No new dependencies, no Electron, no filesystem — this is a pure function of three strings.

**Tech Stack:** `fast-diff`, Vitest.

**PRD:** [`docs/prd/notes-editor.md`](../prd/notes-editor.md) §External writes and FR-5 — "a diff3 that reports conflicts rather than resolving them is the piece to write; the report is what routes the case to reconcile, so a merger that silently picks a side would remove the feature."

---

## Three decisions this plan takes

Each is a genuine fork, and none is in a PRD. Stated here so they are cheap to reverse.

### 1. Line granularity, not character

The PRD mentions `fast-diff`'s semantic cleanup, which is character-level. This plan uses `fast-diff` only as an **LCS engine over lines**.

Merging two edits *inside one paragraph* at character level produces a sentence neither person wrote, silently. That is the failure the whole feature exists to prevent: D60 §5's property is that **ignoring the banner leaves you working on an unbroken vault**, and a plausible-looking merged sentence is worse than a banner because nobody will ever look at it again. Line granularity also makes "conflict" mean the same thing whether it came from `git merge` or from the editor, which is the "one conflict story" the PRD asks for.

**The cost, plainly:** editing a long soft-wrapped paragraph while the agent appends a sentence to that same paragraph will conflict. That is a real case and it will happen. It is the right answer anyway, because the alternative is interleaving two people's prose by character offset.

### 2. Adjacent non-overlapping hunks merge — a deliberate divergence from git

Git conflicts when two changed lines are *adjacent*, because its merge needs an unchanged line between two changes to call them independent hunks. That was narrowed into `prd/tasks.md` two commits ago (`90dcaf3`).

This merger does **not** copy that. Hunks conflict when their base ranges **overlap**, not when they touch. Someone typing at line 10 while the agent edits line 11 should not get a banner — and unlike the git case, these two edits are seconds apart on one machine, where genuine independence is the norm rather than the exception. Git's rule is an artifact of its three-line context model, not a semantic claim, and there is no reason to import the artifact.

Both behaviours get a test, so the divergence is pinned rather than incidental.

### 3. A conflict does not touch the text

`merge3` returns **either** merged text **or** a list of conflict regions. It never returns text with `<<<<<<<` markers in it.

This is the same rule `pull()` follows for the same reason (FR-12): a conflict must never land markers in a file someone is typing into. The editor keeps the user's buffer exactly as it is, stops autosaving it, and shows the banner. The regions exist to build the reconcile prompt from.

## Contracts

```ts
/**
 * One region where both sides changed overlapping base lines.
 *
 * All three slices are carried, because the reconcile prompt is built from them
 * — "here is what it was, here is what you wrote, here is what arrived" is the
 * question the agent has to answer, and two of the three is not enough.
 */
export interface ConflictRegion {
  /** Line offsets are 0-based and index each side's OWN line array, so a caller
   *  can highlight the region in the buffer it already holds. */
  base: { start: number; lines: string[] }
  mine: { start: number; lines: string[] }
  theirs: { start: number; lines: string[] }
}

/** Mirrors `PullResult`'s shape on purpose: one conflict story, whatever
 *  produced it. */
export type Merge3Result =
  | { kind: 'merged'; text: string }
  | { kind: 'conflict'; regions: ConflictRegion[] }

/**
 * `base` is the text last loaded or saved, `mine` is the buffer, `theirs` is
 * what is now on disk.
 *
 * Total: it never throws for content, because every caller is an editor holding
 * unsaved work and a throw there has no honest handler.
 */
export function merge3(base: string, mine: string, theirs: string): Merge3Result

/** A replacement of `base[start, end)` with `lines`. An insertion has
 *  `start === end`; a deletion has an empty `lines`. Exported for its tests. */
export interface Hunk {
  start: number
  end: number
  lines: string[]
}

/** Exported for its tests; `merge3` is the interface callers want. */
export function lineHunks(base: string[], other: string[]): Hunk[]
```

## Gotchas — read before writing code

- **`fast-diff` is character-based.** Line mode is the diff-match-patch trick: map each distinct line to one code unit, diff the two synthetic strings, map back. Do **not** reach for `cleanupSemantic` — it coalesces character runs for human readability and would corrupt a line encoding.
- **The code-unit alphabet runs out at 65536 distinct lines**, and lone surrogates (`0xD800`–`0xDFFF`) must be skipped or a string operation can normalise them away. On overflow, return a **whole-document conflict** rather than a partial merge: it routes to reconcile, loses nothing, and never corrupts. A note with 63k distinct lines is not a note anyone is editing.
- **Splitting on `\n` puts the trailing newline in an empty last element.** `'a\nb\n'.split('\n')` is `['a','b','']`, and joining restores it exactly. Keep that element — dropping it means every merge silently strips the file's final newline, which git then shows as a diff on a line nobody touched.
- **`\r\n` is not normalised.** A CRLF `theirs` against an LF `mine` makes every line differ and conflicts the whole file. Honest, rare (git normalises on checkout), and preferable to a merger that rewrites line endings behind the user's back. Note it; do not fix it here.
- **An insertion is zero-width in base**, so overlap cannot be tested with `start < otherEnd && otherStart < end` alone — two insertions at the same base offset both have `start === end` and would read as non-overlapping. Treat same-position insertions from both sides as a conflict, matching git's add/add.
- **Both sides making the *identical* change is not a conflict.** It is the common case when a user saves and the same content arrives from a pull, and reporting it would put a banner on a file that is already correct.
- **`base === mine` means a clean buffer** — the caller should not have invoked the merge at all, but returning `theirs` verbatim is the only sane answer, and it must not depend on the diff finding nothing.

## Task 3: `merge3` — the conflicts and their report

**Files:** modify `merge3.ts`, `merge3.test.ts`

This is the task the feature exists for. A merger that resolves is worse than no merger.

- [x] **Step 1: Write the failing tests**

`describe('merge3 — conflict')`:
- `conflicts when both sides changed the same line` — assert `kind: 'conflict'` and that **no text is returned**, so the caller cannot accidentally write a resolved buffer.
- `conflicts when the changed ranges overlap partially`.
- `conflicts on two different insertions at the same position` — add/add, matching git.
- `reports the base, mine and theirs slices` — assert all three, with their line offsets. The reconcile prompt needs all three; two of them is not a question the agent can answer.
- `reports offsets into each side's own lines` — construct a case where the three offsets genuinely differ (an earlier one-sided edit shifts them), or the test passes for the wrong reason.
- `reports every conflicting region, not just the first` — two independent overlaps.
- `merges the clean regions and still reports the conflict` — a document with one mergeable edit and one overlap is a conflict overall; assert the clean edit is not silently lost from the report's framing.
- `conflicts when one side deletes a region the other edited` — delete/modify, the case a naive overlap test misses because one hunk has no lines.
- `conflicts the whole document when the line alphabet overflows` — build 70k distinct lines; assert one region covering everything, and that it does not throw.

- [x] **Step 2: Run and watch fail**
- [x] **Step 3: Implement** — on overlap, extend the region greedily while hunks keep overlapping, then emit one `ConflictRegion` with all three slices.
- [x] **Step 4: Run and watch pass**
- [x] **Step 5: Commit** — `feat(shared): a merge that refuses is the point`

## Not in this plan

- **The editor wiring** — holding a base, detecting the external write, deciding clean-vs-dirty, calling this, and showing the banner. Plan 5, and the PRD's own §Open question 2 (how the editor's own save is distinguished from a foreign one) is unresolved.
- **Conflict markers.** Nothing in the product writes them: a git conflict aborts, and this reports. If the reconcile agent ever wants a marked-up rendering, it is a formatter over `ConflictRegion[]`, not a change here.
- **CRLF normalisation** — see the gotcha. A real limit, deliberately not papered over.
- **Word or character granularity** as a second pass inside a conflicting region. Tempting, and exactly the thing decision 1 rejects.
- **Undo semantics across a merge** — PRD §Open question 3, and a CodeMirror transaction question rather than a merge one.

Nothing requires the two mergers to disagree in the same places, and this one being more permissive is a feature: someone editing `status` while a pull lands a new `due` on the next line wants both, and both is unambiguous.

**Two tests of mine were wrong while the code was right**, both in the same direction — I wrote a scenario that did not contain the thing it was named for:

- `reports only the genuine overlap when the rest merged cleanly` used two *non-overlapping* one-sided edits, which merge cleanly and correctly. Rewritten with a real overlap, and it now also asserts the untouched edit does not appear in the report.

Neither was a bug in `merge3`. Worth recording because the pattern — a test that passes for the wrong reason, or fails for one — is the failure mode of writing tests from a plan rather than from the behaviour.

**The test that earns its keep** is `lineHunks`'s last one: apply the hunks back onto base and get `other`. It states the property once instead of asserting shapes case by case, and it is exactly what the merge walk relies on.

Nothing else diverged. The gotchas list held up — in particular the "flush a pending hunk only on EQUAL" rule, without which a rewritten line arrives as a separate delete and insert that the walk cannot recognise as one edit.
