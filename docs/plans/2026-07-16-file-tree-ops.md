# File tree ops — the affordance the agent already has

> **For agentic workers:** use the executing-plans skill. Steps are checkboxes. This plan is **lean by design** — it states contracts, decisions and gotchas. Derive the code.

**Goal:** rename a note, move it, delete it, rename a folder — from the tree, where you look for it.

**The state of play:** `FileTree.tsx` is **create-only** (87 lines; one inline `<form>`, one mutation). There is no rename, no delete, no context menu; `draggable` appears nowhere; `onContextMenu` appears nowhere **in the entire renderer**. The server has all of it, built and tested: `notes.rename`, `notes.renameFolder`, `notes.delete`, `notes.backrefs`. Rename atomically rewrites every `[[link]]` that pointed at the old path (`yjs/rename.ts`, pinned by `test/rename.test.ts`) and snapshots each touched doc first. **The asymmetry that makes this urgent:** the agent *can* rename, via MCP (`agent/mcp-ops.ts:101`) — its tool description explicitly steers it away from `mv` and toward the link-rewriting path. So "ask Claude to rename it" works and does the right thing, while the obvious affordance in the tree does not exist. `notes.renameFolder` and `notes.backrefs` have **zero callers outside server tests**.

**Spec:** `prd/notes-editor.md` FR-11 / FR-12 / FR-13.

## Decisions

| # | Decision |
|---|---|
| **D55** | **Delete surfaces backrefs *before*; tombstones *after* are deferred.** FR-12 wants both — a warning that N notes link here, and `[deleted note]` where those links now dangle. The first half is buildable now and is the half that prevents the loss: `notes.backrefs` is built, tested and **uncalled**, and one query turns "delete this?" into "3 notes link to this — delete anyway?". The second half is not a small addition: **D27 says no cascade**, so a dangling ref survives by design — but the client rendering of that has **no host surface to render into**. Tombstones live in `related[]` (`shared/task-file.ts:404` — a ref whose doc is gone serializes as a raw id so the link survives a round-trip), and `related[]` is **invisible in the renderer**: `TaskDetail.tsx` has no relations row at all, and the strings `tombstone` / `[deleted note]` do not exist in the codebase. So "render tombstones" is really "build the relations surface", a separate known gap that must not be smuggled in behind a delete button. **Shipping the warning without the tombstone is not half a feature** — it is the preventive half, and it is strictly better than today's tree, which cannot delete at all and so warns about nothing. |
| **D56** | **Folders stay implicit, and the tree hides vestigial empty ones rather than deleting their rows.** You make a folder by naming a path (`ensureAncestorFolders`, `paths.ts:18`); there is **no `createFolder`/`deleteFolder` anywhere** and this slice adds none. **But shipping delete creates a problem that cannot exist today:** deleting the last note in a folder leaves an orphan `folders` row, and `buildTree` renders it as an empty folder you cannot remove — and until now you could not delete a note from the tree at all, so nobody could make one. **Why not GC the row on delete: `ON DELETE SET NULL` (D38) means deleting a folder row *unfiles every task pointing at it as its `area`*.** A folder with no docs can legitimately still be a board lane full of tasks — docs and tasks are different populations over the same folders. So a tidy-up in the notes tree would silently empty a lane on the board. **The fix is display and it is confined to the tree:** `buildTree` drops folder nodes with no descendant docs. Since no one can deliberately create an empty folder, an empty folder is *always* vestigial, so hiding it loses nothing — and `foldersAtom` (`state/tasks.ts:35`) keeps feeding the board's lanes untouched. |

## Contract

**Server — one bugfix, no new surface:**
- **`renameFolder` gains `renameNote`'s conflict check.** `renameNote` rejects a taken path with `CONFLICT` (`rename.ts:86`); `renameFolder` (`:100`) checks **nothing** — renaming `a` onto an existing `b` silently merges the two, and a contained-doc collision hits the `docs` unique constraint **mid-loop with no transaction wrapping the move**, leaving half the notes moved. That is data loss, it is reachable the moment a rename button exists, and "wire what exists" does not mean wiring a known trap to a button. Test the conflict **and** that a rejected rename moved nothing.
- Everything else is used as-is. `notes.rename`, `notes.delete`, `notes.backrefs`, and `renameFolder`'s body are correct and tested.

**Desktop — state (`state/vaults.ts`, beside `createNoteAtom`):**
- `renameNoteAtom`, `renameFolderAtom`, `deleteNoteAtom`, `loadBackrefsAtom`. All `vaultProcedure` calls, so **every input needs `vaultId`** (the middleware merges it in — `trpc.ts:52`) from `activeVaultIdAtom`, exactly as `createNoteAtom` does.
- **Do not refetch after a mutation.** `createNoteAtom:28` does `await set(loadDocsAtom)` with the comment `// no subscriptions this phase` — the user-scoped stream plan retires that, and `docs:event` now carries `created`/`renamed`/`deleted` back live. **If that plan has not landed, refetch and leave a comment saying which plan removes it.** Two mechanisms racing to update the tree is worse than either.
- `deleteNoteAtom` must clear `activeDocAtom` when it deletes the open note — otherwise the editor holds a doc that no longer exists.
- `loadBackrefsAtom` returns `Array<{ srcDocId, occurrences }>` — **`srcDocId` only, no path, no title**. Join against `docsAtom` client-side to name them, and handle an id that is not in `docs` (a link from a doc you cannot see) rather than rendering `undefined`.

**Desktop — the pure half (tested headless):**
- `buildTree` (`lib/tree.ts:23`) drops folder nodes with no descendant docs (D56). It is already pure and has the tree's only real logic; test it directly.
- A `renameTarget(node) → { kind: 'note', docId } | { kind: 'folder', folderId } | null` predicate: `null` when a folder node's `folderId` is `null` (see gotchas). Keep the "can this row be renamed" question out of the JSX.
- Path validation mirrors `safePath` (`paths.ts:7`) enough to not send a request the server will `BAD_REQUEST`, and the `.md` suffix rule already in `FileTree.tsx:15`.

**Desktop — UI (`FileTree.tsx`):**
- **Hover-revealed actions on the row + inline rename input.** Match the file's existing inline `<form>` create idiom. **Not a context menu** — `onContextMenu` exists nowhere in the renderer and a menu primitive is net-new; **not a modal** — no modal/dialog/`role="dialog"` primitive exists either. Rename prefills the current path and selects the basename.
- **Rename is also move.** Typing a new path with a different folder prefix moves the note, and the server's `ensureAncestorFolders` makes the destination folders exist. **No drag-and-drop this slice** — rename-to-path covers the semantics, and `BoardView`'s drag is a different shape (a drop target per cell, D42) that would not port.
- Delete: `loadBackrefs` **first**, then a `window.confirm` naming the linking notes (D55) — matching `MembersSection.tsx:65`, the codebase's only destructive-confirm precedent. Zero backrefs still confirms, just without the list.
- **Surface errors.** `FileTree.tsx` currently `void`s its mutation, so a `CONFLICT` from `notes.create` rejects into nothing and the row just… doesn't appear. Rename and delete both have reachable server errors (`CONFLICT` on a taken path, `BAD_REQUEST` on a bad one) and this slice must not add two more silent failures. `VaultSettings`'s `guard()` busy/error wrapper is the house pattern.

## Gotchas

- **`buildTree` synthesizes prefix-only folders with `folderId: null`** (`tree.ts:36`) and **`renameFolder` takes a `folderId`** — so some folder rows are structurally un-renameable. `ensureAncestorFolders` means most have real rows, but the null case is representable and the UI must simply not offer rename there. Do **not** paper over it by renaming the contained docs one by one — that is `renameFolder`'s job and it does it better.
- **`HIDDEN_ROOTS` filters at the root level only** (`tree.ts:21` — `.claude`, `.holi`, `AGENTS.md`, `MEMORY.md`, `CLAUDE.md`). A nested `foo/.holi` renders today. Renaming a note **into** a hidden root would make it vanish from the tree while still existing — worth a guard, and definitely worth not being surprised by.
- **Task files live in the tree too.** `tasks/**.md` is the projector's working copy; renaming or deleting one from the notes tree is not the same act as deleting a task, and the projector will fight you (a file missing at `start()` is **re-materialized**, D40 — it is never read as a delete). Check whether task files reach `buildTree` before shipping a delete button that appears to work and then silently undoes itself.
- **Deleting the open note leaves `activeDocAtom` pointing at a corpse.** The provider is on a room for a doc that is gone.
- **Folder collapse state is `useState` per row, unkeyed and unpersisted** (`FileTree.tsx:44`). A rename changes a row's path — if rows are keyed by path, the row remounts and its subtree springs open. Cosmetic, but the live `docs:event` stream makes the tree re-render far more often than it used to, so it will be noticed.
- **`renameFolder` emits `docs:renamed` per contained doc and *nothing* for the folder itself** (`rename.ts:100`). With `docs:event` live, the tree will therefore see the docs move and infer the folder — which happens to be correct, because folders are derived from doc paths. Know that it is derivation, not an event; a folder rename that moves **zero** docs emits nothing at all and will not appear until a refetch.
- **`notes.delete` and `notes.rename` have no role gate** — any member can do either. Consistent with every other note mutation here; not this slice's decision to revisit.
