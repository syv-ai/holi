# The user-scoped event stream — one connection, every vault

> **For agentic workers:** use the executing-plans skill. Steps are checkboxes. This plan is **lean by design** — it states contracts, decisions and gotchas. Derive the code.

**Goal:** a note a teammate creates appears in your tree. A vault you are invited to appears in your switcher. A reminder fires for a vault you do not have open and still reaches you. All three are the same missing thing: the client has no live channel that is scoped to *you* rather than to one vault.

**The state of play:** the server publishes everything and the client subscribes to almost none of it. `docs` frames reach main and feed **only** the on-disk mirror (`vault-manager.ts:134`) — never the renderer, so `docsAtom` is refetch-only on vault activation (`state/vaults.ts:28`, the `// no subscriptions this phase` comment this plan retires). The switcher has it worse: SSE is mounted at `/events/<vaultId>` (`main.ts:63`), so "you were added to a vault" **has no channel to arrive on at all**. That is also why reminders cannot cross vaults (**D48**). Three tRPC subscriptions (`vaults.watchDocs:74`, `tasks.watch:123`, `reminders.subscribe:23`) look like the answer and are **dead code** — no WS link exists and the IPC link throws on subscriptions (`server-client.ts:39`).

**Spec:** `prd/notes-editor.md` §Panes & tabs (tree presence) · `prd/vaults-collaboration.md` §Shared vault · `prd/tasks.md` §Recurrence & reminders (the user-scoped stream deferred by D48).

## Decisions

| # | Decision |
|---|---|
| **D50** | **The event stream is scoped to a user, not a vault, and the frame carries an envelope: `{ vaultId, event }`.** `GET /events` replaces `GET /events/<vaultId>`; auth keeps `resolveSession` and **drops `resolveVaultRole`** — a user-scoped stream cannot ask "what is your role in *the* vault", so the gate becomes the `memberships`-by-user query `vaults.list` already runs (`vaults.ts:10`, indexed by `memberships_user_idx`). **Why an envelope and not a `vaultId` on the payloads:** none of `DocsEvent`/`TasksEvent`/`PresenceEvent`/`RemindersEvent` carries one, because the bus key `` `docs:${vaultId}` `` always supplied it. Multiplexing is a *transport* concern — the payloads describe **what** happened, the envelope says **where** — and each of those four shapes is hand-mirrored in up to three client files (`vault-manager.ts:24`, `vault-mirror.ts:48`, `state/tasks.ts:18`), so widening them is the **D36** trap: a consumer reading a union exhaustively-by-accident. The envelope is built at subscribe time, where `vaultId` is already a closure variable, so nothing has to demux it back out — including the reminders watermark, which stays keyed `(vaultId, userId)` untouched (**D47**). **Replace, don't add:** two stream routes is two auth models and a dead one. **This closes D48.** |
| **D51** | **Membership is the re-keying signal: a user-keyed bus channel `user:<userId>`, and exactly one place a membership changes.** A user-scoped stream that resolves your vaults at connect is **stale the moment you are invited** — the new vault's frames go to a key nobody is listening on, and the switcher is exactly as broken as before. So the stream subscribes to `user:<id>` and adds/removes the four per-vault listeners live. This is the *only* reason option (b) fixes the switcher and option (a) could not. `wakeEvaluator` (`bus.ts:62`) is the sole precedent for an unscoped key; this is the first *user*-scoped one. **`MembershipEvent = { type: 'joined' | 'left'; vaultId: string }`** — and unlike every other channel the `vaultId` must live in the *payload*. ~~It carries no vaultId; the envelope has it.~~ **That was wrong and was corrected in `cdd7a46`:** the other four channels are keyed `<channel>:<vaultId>`, so the handler lifts the vault out of its closure into the envelope; this one is keyed `user:<userId>`, so the vault is not in the key, and with it absent from the payload it would be nowhere — the listener is told "you joined" with no way to learn what. The handler still lifts it into the same envelope, so the *wire* stays uniform and the desktop mirrors a bare `{ type }`. The asymmetry is bus-vs-wire, and the key forces it. **The client refetches `vaults.list` rather than being handed a `Vault`:** on `left` you can no longer *read* the vault, so a payload carrying it would be a row the server must fetch specially to describe a thing you just lost access to. Refetch is one indexed query and matches `createVaultAtom`'s existing `await set(loadVaultsAtom)`. Following **D35**, membership writes funnel through one helper that emits — a direct `insert into memberships` fires no event, so a live stream never re-keys and the invitee's switcher stays empty until restart. That is today's bug, and the funnel is what stops it coming back. |
| **D52** | **Main filters `docs`/`tasks`/`presence` to the active vault; `reminders` and `membership` are never filtered — and so `reminders:open` gains a `vaultId` and switches vault before selecting the task.** The renderer holds exactly one vault's tree and one vault's board; a frame for a vault with no mirror and no projector has nowhere to go (`vault-manager.ts:75` holds one `current`). Filtering in main keeps `tasks:event`/`tasks:presence` **bare-payload and unchanged**, so the board carries no regression risk from this slice, and the renderer never learns to filter by a vault id it has no use for. Reminders are the deliberate exception — delivering them for vaults you do *not* have open **is** the closure of D48, and there is no point transporting them user-scoped only to drop them in main. **The consequence is real and must ship with it:** a cross-vault reminder's notification click currently does `setView('board'); setSelectedTaskId(taskId)` (`Shell.tsx:63`) against the *wrong vault* — the task is not there, so the click silently selects nothing. The payload becomes `{ vaultId, taskId }` and the handler activates the vault first. A notification you cannot act on is worse than one you never got. |

## Contract

**Server — the bus (`apps/server/src/bus.ts`):**
- `MembershipEvent = { type: 'joined' | 'left' }`; `emitMembership(userId, event)` → key `` `user:${userId}` ``. No `vaultId` in the payload (D51).
- The four existing `emit*` signatures and payload shapes are **untouched**. This slice adds a key; it widens nothing.

**Server — one place a membership changes (D51):**
- A helper (`membership/service.ts`, beside D49's ops) that inserts/deletes the row **and** emits. The writers, verified by grep: `membership/service.ts:58` (invite), `:82` (remove), `:94` (leave), plus **`routers/vaults.ts:32` (create)** and **`auth/provision.ts:17` (personal provisioning)**. Re-grep before you start — the funnel is the point, and one missed writer is a switcher that silently stays stale.
- **The emit must happen after the transaction commits, not inside it.** `vaults.ts:32` and `provision.ts:17` both `tx.insert(memberships)` inside a `db.transaction`, and the bus is an in-process `EventEmitter` with **no transactional semantics** — emitting inside the tx announces a membership that can still roll back, and the client would subscribe to a vault that never existed. So the helper either takes the tx and returns a deferred emit for the caller to fire on success, or the caller emits after commit. Whichever shape, **a test must pin that a rolled-back transaction emits nothing** — this is invisible on the happy path and only ever fails in production.
- `transferOwnership` (`service.ts:111`,`:115`) and `setRole` (`:71`) emit **nothing**: a role change is not a join or a leave, and the vault *list* does not render role. The Members panel already refetches on its own mutations.
- **`test/fixtures.ts:18`/`:23` insert memberships directly** and will not emit. That is fine — and it is a trap: a test that seeds with `seedVault`/`addMember` and then asserts the stream re-keyed will pass vacuously or fail confusingly. The re-keying test (task 3) must go through the **real** `invite` path.

**Server — the stream (`apps/server/src/events.ts`, `main.ts:63`):**
- Route `GET /events`, no path param. The regex branch in `main.ts` narrows to a literal; the `([0-9a-f-]{36})` capture goes away.
- Auth: `resolveSession` unchanged (`user.id` is already in scope for the whole connection). `resolveVaultRole` is **gone** — 401 on no session, and that is the only gate. Membership is now a *subscription set*, not an admission check.
- Per-connection: `subs: Map<vaultId, teardown>`. `subscribeVault(vaultId)` binds the four channels with `vaultId` captured, each sending `{ vaultId, event }`. Seed from the memberships-by-user query; then `bus.on('user:<id>')` → `joined` ⇒ `subscribeVault`, `left` ⇒ teardown. Tear down **every** sub plus the user key on close — the existing single-vault teardown (`events.ts:51`) becomes a loop, and a leaked listener per reconnect is a real leak on a `setMaxListeners(0)` bus.
- `markDelivered(db, vaultId, user.id, e.firedAt)` stays exactly as-is inside the reminders binding — `vaultId` is the closure variable, so D47's ledger needs no change at all.
- Frame format (`event: <channel>\ndata: <json>`), the `:connected` preamble and the 25s heartbeat are unchanged. Still no `id:`/`Last-Event-ID` — resume stays out of scope; recovery is reconnect-then-reconcile, as today.
- **Delete the three dead tRPC subscriptions** (`vaults.watchDocs`, `tasks.watch`, `reminders.subscribe`). They advertise a transport that does not exist and now never will; leaving them is leaving a second, wrong answer next to the right one.

**Server — reminders catch-up:**
- `reminders.catchUpAll`: `authedProcedure`, **no `vaultId`** — loops the user's memberships and calls the existing `catchUpDeliveries(db, vaultId, userId)` (`delivery.ts:52`) per vault. Replaces `vault-manager.ts:172`'s `client.reminders.catchUp.mutate({ vaultId })`. **Why server-side:** on reconnect *every* subscribed vault missed fires, and a client loop needs the vault list in main plus N round trips to do worse.
- **It must return the fires grouped by vault** — `Array<{ vaultId, missed }>`, not a flat concat. Today's `catchUp` returns bare `missed` because the caller already knew the vault; under D52 the notifier needs a `vaultId` per fire to make the notification clickable, and a flat list has thrown away the only thing that could supply it. Getting this wrong reproduces exactly the bug D52 exists to prevent, on the catch-up path instead of the live one.
- **`reminders.catchUp` (per-vault) keeps its only caller in `vault-manager.ts` — which this slice deletes.** Check for others; if there are none, delete it rather than leave a second way to do the same thing.

**Desktop — main:**
- New `main/events/user-stream.ts`: owns the one `SseClient` at `${API_URL}/events`, **started at sign-in and stopped at sign-out** — not at `activate`. It is a dumb transport: parses the envelope, calls `onEnvelope(channel, vaultId, event)`. `SseClient` itself is unchanged (fetch-based for the `Authorization` header; capped backoff; `onReconnect` fires only on *re*-connect).
- `vault-manager.ts` **stops owning the stream**. `activate` no longer constructs an `SseClient`, and no longer calls `catchUpReminders` (the stream now covers every vault continuously, so the per-activation catch-up D48 forced is dissolved). It keeps `current`, the mirror, the projector, and the ordering comments that survive.
- `vaultManager.handleEnvelope(channel, vaultId, event)` is the dispatcher (D52):
  - `docs` → active-vault only → `mirror.handleDocsEvent(event)` **and** `deps.send?.('docs:event', event)`. The mirror still needs it — this is an addition beside the existing call, not a redirect.
  - `tasks` / `presence` → active-vault only → existing logic verbatim, bare payload.
  - `reminders` → **no filter** → `deps.onReminders?.(vaultId, event)`.
  - `membership` → **no filter** → `deps.send?.('vaults:event', event)`.
- `onReconnect` → for the **active vault only**: `mirror.refresh()` + `projector.reconcile()` (no other vault has local state to reconcile — theirs is refetched when you activate them). Plus `reminders.catchUpAll` and a `stream:resync` push so the renderer refetches vaults **and** docs. With no resume cursor, reconnect is the only gap recovery there is, and the tree/switcher must be part of it or this slice reintroduces staleness on exactly the path it exists to fix.
- Startup order: stream up → `catchUpAll` (a fire while the app was closed), mirroring the old "after the stream is up so a fire in the gap isn't missed by both" comment at `vault-manager.ts:186`.
- `reminders/notifier.ts` → `send('reminders:open', { vaultId, taskId })` (D52). The coalesced summary still carries **no** `taskId` (it speaks for several tasks) — but it **does** carry `vaultId`, so the click can still land you in the right vault.

**Desktop — preload + `global.d.ts`:**
- `pushChannel<unknown>('docs:event')`, `pushChannel<unknown>('vaults:event')`, `pushChannel<unknown>('stream:resync')`. New `docs: { onEvent }` namespace (there is none today); `vaults:event` + `stream:resync` sit next to `vault: { activate }`.
- `global.d.ts` is the **only** typed declaration of `window.holi` — preload is deliberately `unknown`. Every push channel there carries a doc comment ("Each returns its unsubscribe closure…"); match it. `reminders.onOpen`'s payload type gains `vaultId`.

**Desktop — renderer:**
- `applyDocsEvent(state: { docs, folders }, event: DocsEvent)` — **pure, exported, tested directly**, under a `// --- reducers` banner in `state/vaults.ts`, exactly as `applyTasksEvent` sits in `state/tasks.ts:42`. `created` ⇒ append; `renamed` ⇒ replace by `doc.id`; `deleted` ⇒ drop by id. Mirror `DocsEvent` locally from `bus.ts:6` with the house comment (`vault-mirror.ts:48` is the wording) — the bus types are server-internal; `@holi/shared` is the client↔server seam.
- Listener in `Shell.tsx` beside `reminders.onOpen` (mounted there, not in a view, because the tree can be off-screen): `setDocs((prev) => applyDocsEvent(prev, e))`.
- `vaults:event` → `void set(loadVaultsAtom)` (D51). `stream:resync` → `loadVaultsAtom` + `loadDocsAtom`.
- **Folder rows have no channel.** `DocsEvent` carries a `DocMeta` only, so a note created into a *brand-new* folder adds no `folders` row locally. `buildTree` synthesizes prefix folders (`tree.ts:36`, `folderId: null`) so the **tree** still renders — but `foldersAtom` (`state/tasks.ts:35`, derived from `docsAtom`) drives the board's lanes, and a null-id folder is un-renameable by the file-tree slice. So: on `created`/`renamed`, if any ancestor path of `doc.path` is absent from `folders`, `void set(loadDocsAtom)`. Cheap, rare (first note in a new folder), and it keeps real folder ids flowing.
- `reminders.onOpen` handler: `vaultId !== activeVaultId` ⇒ set `activeVaultIdAtom` first, then `setView('board')` + `setSelectedTaskId(taskId)`. Shell's existing activation effect does the rest.

## Gotchas

- **The renderer must still never open a stream.** The invariant loosens from "one connection per vault" to "one per user" — main still owns it (`vault-manager.ts:68`, `index.ts:71`). Both comments state the old rule and must be rewritten, not deleted; the rule they protect survives.
- **`activate` early-returns on the same vault (`vault-manager.ts:98`) and tears down on every switch (`:99`).** The stream must sit *outside* that lifecycle entirely — if it is created anywhere reachable from `activate`, vault switching silently reconnects it, and you get back the churn this slice removes plus a missed-fire window on every switch.
- **Deactivate ordering is load-bearing** (`observer.onDeactivating` first — open agent turns must merge through a live mirror). Don't disturb it while lifting the stream out.
- **A frame for a non-active vault must not reach `mirror` or `projector`.** They are constructed inside `activate` and close over one vault. `applyTasksEvent` on the projector reads `upserted … else remove(taskId)` — a foreign frame falling through **deletes a task file** (D36's trap, reached by a new road).
- **`markDelivered` fires on *send*, not on receipt.** Sending *is* delivering (D47). Now that the stream carries every vault, a fire for a vault you have open in *no* window is still marked delivered the moment it is written to the socket — which is correct and is precisely what D48 was waiting for, but it means a dropped frame is a lost reminder. Unchanged risk, wider blast radius; do not "improve" it into a client ack in this slice.
- **`resolveVaultRole` is still right everywhere else.** It goes away *only* in `events.ts`. `vaultProcedure`, `requireDocAccess` and the relay's `onAuthenticate` all still gate per-vault and must keep doing so — the stream getting broader does not make authorization broader.
- **`vaults.list` is the membership query, and it returns `Vault`s.** The stream wants ids; reuse the join (`vaults.ts:10`), don't re-derive the predicate. Two answers to "which vaults is this user in" is how the stream ends up subscribing to a set the API disagrees with.
- **`bus.setMaxListeners(0)`** (`bus.ts:70`) means a listener leak raises **no warning**. The teardown loop is the only thing standing between a reconnect storm and unbounded listeners — hence the `listenerCount` assertion in task 3.
- **Single-node bus** (`bus.ts:1`) gets slightly worse here: a user's whole vault set must now be reachable from the one node holding their connection. Unchanged for v1 (single node by design), but it is a real note for the multi-node question, not a rounding error — record it where that question lives.
- **`takenAt`-style date drift:** there is no superjson transformer on the ipcLink, so server `Date`s arrive as ISO strings in the renderer. Nothing in this slice sends a `Date` — keep it that way.
