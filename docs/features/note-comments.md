# Note comments

A note can carry comment threads, the way a shared draft gets reviewed: each thread is about a passage of the note and holds comments with an author, a time and replies, open until someone resolves it. The threads live beside the note, never in its text, so its diffs and anything exported from it stay clean. The agent reads and answers them with `holi comments`.

## How it works

**A sidecar per note.** A note's threads are `.holi/comments/<note path>.json`, committed and synced like the note. Threads and comments are objects keyed by a short random id, never arrays, and the file is written with its keys sorted (`formatRecord`), so equal threads are equal bytes. A comment has an author (a GitHub login), an ISO time, a markdown body and, when the agent wrote it, `agent: true`. Only `holi comments` sets that flag: a comment written through `comments.*` from the window is the person's own, whether or not their agent is running beside it. A thread has the passage it is about (its anchor), its comments and its last resolve or reopen (`status`, with who and when); one with no status is open. Holi checks only the fields it uses: a key it does not know, and a thread or comment it cannot read, are kept in the file and written back as they came, by every write and every merge; `holi comments` just does not list them. A file that is not a JSON object, or whose `threads` is not one, is refused, never written over, and so is a sidecar path that is a symlink or differs in case from the file on disk (`exactPath`): a sidecar arrives with a pull, so a link committed in its place must not let a read or a write reach another file.

**Anchored to a quote.** A thread holds the passage it was made on, up to 32 characters of text either side, and the line it started on, the way the W3C's TextQuoteSelector does. It is placed again whenever the note is read (`locateAnchor`), first match wins: the quote exactly, wherever it moved, repeats told apart by their context and then by nearness to the line; else whatever now sits between its prefix and suffix, at a plausible length (the passage was edited in place); else a span from the quote's first third to its last third (edited in the middle). A thread that none of these finds is **detached**: listed by `holi comments list` with its quote, never dropped.

**What takes threads.** A file a running plugin owns has no threads (a task file; with the tasks plugin off it is a note and takes them); a claim that only adds to a note, such as the PDF plugin's Convert to PDF, leaves it a note, and neither does the agent surface (`AGENTS.md`, `CLAUDE.md`, `MEMORY.md`, `USER.local.md`, `.claude/**`, `.holi/memory/**`, `.holi/schedules/**`), which is the agent's instructions rather than a document to review: the router and `holi comments` refuse them (`isCommentableNote`). The threads read are the open vault's; switching vaults starts from none.

**Not in the window yet.** The passages' fill in the editor, the selection's **Comment**, the panel (open and resolved threads, Reply, Resolve, Reopen, `@login` completion) were drawn on the previous shell and are not rebuilt on the document editor ([not-built](../not-built.md)). `comments.*` in the router is what they will call. A comment the agent wrote is shown as "_login_ via agent" in the inbox and `holi comments list` alike (`commentByline`).

**Merging.** Two people commenting at once must not pause sync. A merge driver, `holi-comments`, claims `.holi/comments/**/*.json` the way app records have theirs ([vaults-sync](vaults-sync.md)): threads and comments are unioned by id, a thread or comment deleted on one side and changed on the other is kept, and a resolve against a reopen keeps the later. Keys it does not know merge the same way, one side's change winning. It refuses text that is not a sidecar, and one value both sides changed with no rule to settle it (a comment's text, a thread's anchor, a key it does not know), which git then records as an ordinary conflict for reconcile rather than keeping one side and dropping the other (`mergeCommentsText`). A comment written in Holi while a pull lands is merged the same way: the sidecar is read again just before the write, and one that changed since is merged rather than written over. A sidecar changed on one side and deleted on the other (the note deleted while someone commented on it) never reaches the driver; a pull or a reconcile keeps the changed sidecar and, when nothing else conflicts, finishes the merge, so the comment survives as a detached thread of a note that is gone.

**Moving and deleting.** A note Holi moves (a rename, a move in the tree, a task's lane, the archive) takes its sidecar along at the moment of the move (`moveNoteComments`); one already at the destination is merged with it, never written over. A note moved outside Holi, by `git mv` or by the agent, is followed by the commit-time `relink` transform, where git has paired the move's delete and add; a sidecar already at the new path is left alone. Git pairs them by guess (half the lines alike), so a note moved and rewritten in one commit can read as a delete and an add, and its threads then stay at the old path, detached. A deleted note's sidecar is never deleted with it: its threads stay, detached, listed by `holi comments list` as on a note that is gone, and the agent can still reply to or resolve them. Nothing deletes a comment but a person removing the sidecar.

**Mentions.** `@login` in a comment mentions a teammate. With no server, a mention arrives with the commit that carries it: after a pull merges, or a reconcile's merge lands, Holi diffs the sidecars it changed (with rename detection, so a sidecar that moved with its note is compared with itself at its old path), finds the comments new to them that mention the person signed in and were written by someone else, and hands each to the plugins (`PluginCtx.onMention`). The agent plugin adds an inbox entry, "_login_ mentioned you", with the passage and the comment, opening the note ([agent-inbox](agent-inbox.md)); the inbox raises the banner by its own quiet rules. A mention written on this machine raises nothing here, and neither does a merge someone runs by hand in a terminal.

**The agent.** `holi comments list [path]` prints a note's threads with their passage, line or detached, comments, replies and status (`--json` for ids), or, with no path, every note with open threads. `add <path> <quote> <body>` opens a thread on text quoted exactly from the note, refusing a quote that is not there and asking for `--line` when it repeats; `reply <path> <thread> <body>` answers, both reading the body from stdin when it is not given; `resolve` and `reopen` take a thread id. What the agent writes is signed with the signed-in login and marked `agent: true`, shown as "_login_ via agent". This CLI is the only writer that sets the flag. `list` is seeded into `permissions.allow`; the writes ask, since teammates see them. Teammates are trusted to write a sidecar, but what `list` prints is still data, not instructions: each body and passage is shown as quoted data (`> ` lines), and the author, resolver, ids and times are printed only in their own shapes (a login's letters, digits and hyphens, a short token, a parsed time), so a sidecar cannot add lines of its own to the output. The shipped `note-comments` skill says how to answer threads (change the note, reply, resolve only what is addressed) and how to review a note.

## Rules

- A thread never touches the note's text. Exported PDFs, diffs and other tools see the note alone.
- A thread is never dropped for losing its passage or its note; detached is a state, not a deletion.
- Only the person signed in writes, under their own login. Holi checks no permissions of its own ([auth](auth.md)): anyone who can push can write a sidecar.
- Anchors are not rewritten as a note changes. A thread keeps the passage it was made on, and the line hint only breaks ties, so a sidecar changes only when someone comments.
- The `<!-- -->` banners ([editor](editor.md)) stay as they are: text in the note, unrelated to threads.

## Rejected

- Comments inside the note (HTML comments, footnotes, CriticMarkup): they show in diffs and exports and have to be removed by hand, which is the problem this solves.
- One file of comments for the whole vault: every comment anywhere would touch the same file, and a merge would involve everyone who commented on anything.
- Arrays of threads and comments: two comments added at once are two insertions at one index, a text conflict; keyed by id they are two keys.
- Character offsets or line numbers as the anchor: any edit above a thread moves it.
- Rewriting anchors as the note changes: churn in a shared file on every edit, from every machine that has the note open.
- A notification service: there is no server. A mention reaches a teammate with their next pull.
