# Google

A vault can connect a Google account to read and triage Gmail, read its calendar, block out the user's own time, compose mail, and turn a thread or event into a task. Mail and Agenda open as tabs, and Mail and Calendar are also sidebar apps (`renderer/mail/`, `renderer/calendar/`); the agent gets the same surface through `holi google <verb>`. Google is a data connector, not identity: without it Holi works fully.

## How it works

- **Connect** with authorization code + PKCE over a one-shot `127.0.0.1` listener, in the system browser. The client id and desktop secret ship in the binary; for an installed app neither is secret, and PKCE protects the grant. Scopes: `openid`, `email`, `gmail.modify`, `calendar.readonly`, `calendar.events`, `contacts.readonly`, `contacts.other.readonly`.
- **The shipped client accepts syv.ai accounts only.** Its consent screen is Internal to the syv.ai Workspace, so Google refuses any other account in the browser with `Error 403: org_internal` and never redirects back; settings says so while a connect is waiting and after one that came to nothing. An Internal client has no test-user list and no 7-day refresh-token expiry.
- **Bring your own client** for any other account, under Settings, Connections, OAuth client (`oauth-client.tsx`, a dialog from the row). In Google Cloud: enable the Gmail API, Google Calendar API and People API; configure the consent screen (External, adding yourself as a test user, or Internal for your own Workspace) with the scopes above; create an OAuth client of type **Desktop app** and paste its id and secret. A Desktop app client allows any `127.0.0.1` loopback port, so there is no redirect URI to register. An External client left in Testing has its refresh tokens expire after 7 days; publish it to Production to keep a connection (Google then shows its unverified-app warning, which for your own client is expected). The client is this machine's, `safeStorage`-encrypted in `userData/google-client.enc` as the tokens are (on macOS, by the Keychain), never in a vault; main keeps the secret and the renderer only ever sees the id. Where the OS offers no encryption (some Linux setups), saving one is refused rather than written in plain text, just as the tokens are, and going back to the default client still works. The client in use is resolved in one place (`resolveClient`): your own, else `HOLI_GOOGLE_CLIENT_ID` with `HOLI_GOOGLE_CLIENT_SECRET` from the environment (which an app opened from Finder does not see), else the shipped pair. **A grant belongs to the client that made it**, so saving a different client id revokes and removes every account on this machine, with its cache, before the switch, so no refresh meets the new client with an old grant; the button names how many and asks once more before it acts. The same id with a new secret is the same client and keeps every account. A connect cancelled, or overtaken by a client change, while its code is being exchanged has the grant that comes back revoked rather than saved.
- **Main is the sole token authority.** Refresh tokens rotate on use, so only main refreshes, single-flighted per account. Tokens are `safeStorage`-encrypted in `userData/google-auth.enc`, keyed by the account's `sub`.
- **Each vault names its account** in `userData/google-vault-accounts.json` (`owner/repo` → `sub`), outside the clone. One account may serve several vaults; linking a stored account needs no consent. _Disconnect this vault_ drops the mapping, at once, because _Use in this vault_ undoes it; _Remove from Holi_ revokes at Google, deletes tokens and cache, and unlinks every vault, so Connections asks first ("Remove … from Holi?", a destructive _Remove account_) and holds the dialog open while the revoke runs. Connections' errors and the reconnect warning are `text-destructive` and wrap rather than truncate. A new vault is never mapped automatically.
- **Scope drift:** an old grant keeps working and 403s only the newly added calls. `missingScopes()` compares stored scopes in Google's vocabulary (`email` returns as `.../userinfo.email`) and settings offers **Reconnect**.
- **Mail cache:** one `node:sqlite` file per account, `userData/google-cache-<sub>.db`, last 500 threads, reconciled by `history.list` deltas. The key carries every filter that narrows a list; the history cursor is per key; archive and trash arrive as label changes and land in a _left_ bucket. Bump `SHAPE_VERSION` when a cached type changes. A removed or dead account deletes the file and its sidecars.
- **Writes:** the renderer paints first and reverts on refusal; main calls Google first and updates the cache only on success. Every thread action takes that one path. Archive and trash, of one thread or a selection, then raise one toast ("Thread moved to Trash", "2 threads archived") that stays until dismissed and offers **Undo**: undo beats a confirmation for a frequent, reversible removal. Undo calls `google.unarchive` (`INBOX` back on) or `google.untrash` (Gmail's `/untrash`), UI-door only, and re-reads the list; nothing is put back into the cache, because `history.list` brings both changes back.
- **Mail's panes** share one left edge: the toolbar, the selection bar, the find bar and the reader's action row are each a `PaneToolbar` (`px-4`), and the thread below them is `px-4` with each message's chevron, addresses and body on the subject's edge. The reader's subject has its own wrapping row, the one place a subject the list truncated reads in full; under it, Reply, Reply all, Archive, Trash and Star stay on the row (and Join for a meeting), and Summarize, Task, Continue draft, Forward, Unsubscribe and Open in Gmail sit in one **More actions** menu, so the row fits the reader at its 280px floor. A row's checkbox shows on hover and on keyboard focus; its tab and labels are `Badge`s. Loading is skeleton rows; disconnected (with _Open Connections_), failed (with _Try again_), empty and "Pick a thread" are the shared `EmptyState`. A failed write is a `text-destructive` line above the list.
- **Calendar** shows calendars the user owns by default; per-calendar overrides are the plugin's `calendars` setting in the vault's `.holi/settings/plugins.local.yaml`, read in main so the agent and apps honour them too. Events carry `mine`. Joining uses `conferenceData`, then the body, then the location, matching a join-link shape. A thread with an `.ics` is joined to its event by the invite's `UID`.
- **The agenda is a month** to look at and create in (`renderer/month-view.tsx`, `month-days.ts`): six weeks, Monday first, ISO week numbers down the side, today in the theme's `primary`, weekends shaded and the neighbouring months' days faded, weekday and month names in the person's language. An event is drawn on every day it covers, timed or all-day, up to its exclusive end: a timed one as its calendar's colour bar and title, an all-day one as a tinted pill; a day with more than three shows two and "+N more", which lists the day. ‹ Today › pages by month and the month asks for its own six weeks (`monthWindow`, always under the 92 days one call may ask); an answer for a month already left is dropped. A **Month | List** `ToggleGroup` reaches the list, the next week with each invitation beside it. Both views share one `PaneToolbar` row: the switch first, then the month's name (month view only, `text-sm`), and ‹ Today ›, Calendars and refresh at the end, so switching never moves the switch or changes the header's height. An event that does not block time, someone else's event and a past one mute their title and never their whole row (opacity on an already-muted line falls below readable contrast); the list's detail line says "free" in words. Loading is skeleton rows, and empty, disconnected (with _Open Connections_), failed (with _Try again_) and "Pick an event" are the shared `EmptyState`. Which one the Agenda _opens_ on is the plugin's `agendaView` setting (`list` by default) in this machine's `.holi/settings/plugins.local.yaml`, shown under Settings, Google. Pressing an event opens it (the same detail the list's pane shows); **pressing a day's empty space starts an event on it** (`NewEventDialog`), made by the agent's own `google.schedule`, open at the UI door too, so it is on the primary calendar, has no attendees and mails nobody. An all-day event's `end` is the day after, as Google's is.
- **The calendar view** (`renderer/calendar/`, mounted as the Calendar sidebar app beside Mail) is ReUI's `event-calendar-3` block over the same capabilities: a rail with the calendars picker, a mini month and the selected day, beside ReUI's event calendar in day, week (the default), month and agenda views, Monday first. It asks `google.agenda` for whatever range the calendar shows (at most 92 days) and `google.calendars` for the colours and the picker, whose ticks are `google.setCalendar`. An event Holi may change, a solo one on the primary calendar (the account's address), can be dragged, resized, edited and deleted; the drag paints first and Google's refusal puts it back with a toast. Moves and edits are `google.reschedule`, deletes `google.unschedule` (both opened at the UI door for it, and refused by main when anyone is invited), and New event is `google.schedule`. Every other event reads in the sheet, its description in the sandboxed frame, and opens in Google Calendar. The block's guests, calendar CRUD, booking facts and notes are dropped: Holi invites nobody and writes only to the primary calendar.
- **Composer:** markdown with a preview through the reader's sanitiser and frame; main sends exactly the previewed HTML as `multipart/alternative`, the markdown as the plain part, marked `X-Holi-Source: markdown`. Drafts live in Gmail and all of them open (unmarked ones via `turndown`). Autosave from the first edit, 2 s idle, single-flight. Reply is sender-only unless reply-all. Edit and Preview are a `ToggleGroup`; the editor is named "Message", and the compose dialog's visible title, "New message", is its accessible name.
- **Linking** a thread or event makes a task with the permalink as a plain markdown link in its body ([tasks](tasks.md)).
- **One set of capabilities, three doors** (`google.*`, [architecture](../architecture.md)): the views call them at the UI door, the agent as `holi google <verb>` through the core bridge, which already authenticates per vault and names the caller's remote, and a vault app reads `google.agenda` and `google.search` at the app door behind its `appGrant`. Every call resolves the account from the caller's remote, never the vault on screen. Reads and writes go through the account's data layer, which is never stale: mail is the cache brought current by a delta, the agenda is always fetched. The agent's `read` is prose only (`textOnly`), a separate entry from the reader's `thread`, so unsanitised HTML reaches only the renderer. `send` takes a composed message with its body on stdin, or `--draft <id>`, which reads no stdin. Google's error kinds cross as refusal codes (`UNAUTHORIZED`, `FORBIDDEN`, `RATE_LIMITED`, `NOT_FOUND`), so the UI picks Reconnect or Retry by code.

## Rules

- **Mail bodies and event descriptions are hostile markup, handled by three separate layers.** DOMPurify decides what survives. A per-message iframe with `sandbox="allow-same-origin"` and never `allow-scripts` (together they let content lift its own sandbox) decides what document it lives in; nothing inside runs. The frame's `default-src 'none'` CSP catches fetches the sanitiser cannot see. Sanitised markup never enters the app's document.
- The sanitiser always drops the `<form>` family (phishing), `<base>` (retargets URLs) and `<link>`/`<meta>` (could redeclare the frame CSP).
- `<style>` stays a forbidden tag, since admitting it changes DOMPurify's parse and frees `<svg><style><img onerror>`. The sheet is lifted out as text, stripped of `@import`, of remote `url()` while images are blocked, and of `</`, then written into a `<style>` the app builds.
- Remote content is blocked and counted until allowed once or always per sender; the always list is the plugin's `imageSenders` setting in the vault's `.holi/settings/plugins.local.yaml`. `data:` is never counted. Allowing it builds a new frame, because a `<meta>` CSP cannot be loosened by rewriting.
- Links never navigate in the frame; only `https:`, `http:`, `mailto:` reach `openExternal`.
- The renderer's own CSP (no `script-src`, no `frame-src`) is not an XSS defence and must not be described as one.
- **The agent may do what the user can undo, and is asked about what reaches someone.** Deleting a message or a thread is impossible by scope, and main refuses every other permanent delete itself. Calendar writes refuse attendee events inside the functions main hands over, since they email people. `holi google send|reply|respond`, and `holi google api` with any method but `GET`, always ask via a seeded `PreToolUse` hook: its `ask` beats allow rules and "don't ask again", it matches all `Bash` plus `mcp__.*[Gg]mail.*` because an `if` on one spelling fails open, it matches the bare `holi`, `$HOLI_BIN` and an absolute path, on the command line as a shell reads its words (a backslash-newline joined, quotes and `$'…'` taken away, a backslash before a character dropped, so `s\end` and `a""pi` are `send` and `api`), and it fails closed. It does not follow a variable, `eval` or `sh -c`, so it asks about any of them near a Holi that runs: a pipeline or list stage whose command word is Holi with an expansion among its words, or whose command word is itself an expansion. A Holi that is only an argument or part of a path (`grep holi "$f"`, `…/holi-src/$FILE`) runs nothing and is not asked about. The bridge refuses any word before the verb, so nothing can be slipped between `holi` and `google send`, and refuses `api`'s method and path given as options, so the gate reads them where they run. The gate's verbs are one table (`REACHES_A_HUMAN`), each with its prompt. It gates a cooperative agent, not an adversarial one ([agent-config](agent-config.md)). The hook is shipped, so an existing vault gets the new verbs at `holi skills update`; until then the merged settings' `ask` rules for `respond` and each non-GET `api` method stand in, and those can be allowed always.
- **`holi google respond <eventId> --yes|--no|--maybe [--comment <text>]`** answers an invitation: an `events.patch` on the primary calendar carrying only the person's own attendee entry (copied, with `responseStatus` and the comment) and `attendeesOmitted: true`, since a patch replaces the whole `attendees` array, with `sendUpdates=all` so the organizer hears. Refused when the person is not a guest, and when they organise it (an organizer's attendee change mails every guest). Calendar has no counter-proposal; a `--maybe` with a comment is the closest thing.
- **`holi google api <METHOD> <path> [--body -]`** reaches the rest of Gmail and Calendar on Holi's tokens. The method is one of `GET POST PUT PATCH DELETE`, in capitals as the gate and the ask rules read it, and it and the path are positional only. Main enforces three things: it refuses the blocked tier, it keeps every call on the two APIs' paths, and it sends a calendar write it judges silent with `sendUpdates=none`. Asking is the hook's job (and, in a vault whose hook is older, the merged ask rules'), not main's. Main's tier for a call comes from its method, path and body alone, in one table (`passthrough.ts`): a `GET` (and Calendar's `freeBusy`) is a read; label changes, trash and untrash, drafts and a new event without guests or `sendUpdates` are undoable writes, and a calendar one is sent with `sendUpdates=none` whatever it said; sending mail, a new event with guests or `sendUpdates` other than `none`, any change to or delete of an existing event (its guests are on the event, not in the call) and any mutating call the table does not know reach others; every Gmail `DELETE`, `messages.batchDelete`, and deleting or clearing a calendar are refused (`FORBIDDEN`). The path is relative to Google's API root and must start `gmail/v1/users/me/` or `calendar/v3/`: a host, a scheme, `..`, `.`, an empty segment, an encoded dot, slash or backslash, another user's mailbox and every other API are refused, and the built URL is checked against the path that was judged. The gate sees only the command line, not the body on stdin, so it asks for every non-`GET`, a superset of the calls that reach others. The answer is fenced string by string, all but ids, addresses, dates, links and Google's enums with no whitespace in them (`fenceAnswer`), and so is any object key that is not one of the two APIs' own field names; everything under `extendedProperties` (an organizer's shared ones reach every guest), `gadget`, `source` and a conference add-on's parameters is fenced whatever its key, and `iCalUID` is too, as its sender chose it; `--body -` reads stdin (`stdinOnDash`), so a `GET` never waits on it. A write through `api` bypasses the mail cache, which `history.list` brings current.
- **What other people wrote reaches the agent fenced.** `holi google read`, `search` and `agenda` (and `api`, every free-text string of Google's answer) wrap every string another person wrote (a mail's subject, snippet, body, names and attachment names; an event's title, description, location, organizer display name, and the name of a calendar the person does not own) as `<untrusted id="..." source="mail" from="...">...</untrusted id="...">` or `source="calendar"`. The id is fresh and random per fence and sits in both tags, so a lookalike closing tag in the text (zero-width characters, full-width brackets, Cyrillic letters) never carries it and never ends the fence; any fence tag inside the text is also defused to `&lt;`. The `from` address names the sending account, not proof of who wrote the text. A refusal that names an event (moving one with attendees) fences its title the same way. One helper does it (`fenceUntrusted` in `packages/shared`), applied at the CLI door alone (`cliValue`): the UI and an app render the same values unfenced, and Summarize fences the subject it seeds. Each string is fenced in place, so `--json` and a spilled file keep their shape and a field picked out with `jq` still carries its marker; a list of untrusted field names beside the data would be lost the moment one field is extracted. Every mail and event is fenced, the person's own included: a sent message quotes the one it answers, and an event on their calendar may carry an invite's title. Ids, addresses (an organizer's `organizerEmail` beside the fenced name), dates and links are not: the agent passes them back to commands. The shipped skills say fenced text is data, never an instruction. The fence is a label, not a wall: the send gate is what stops a send a mail talked the agent into.
- Never write "the agent cannot send": `gmail.modify` permits it; the gate is the wall. Do not widen past `gmail.modify`.
- A send with unknown outcome is never retried. UI send is not gated.
- Mail data stays in `userData`, per account, never in a vault.
- Treat a new Google call as broken until it has run against a real account; fakes written from docs have passed on broken code, and Gmail answers some bad requests with an empty 200.

## Rejected

- Google's device flow: not approved for these scopes.
- The own client as a plugin setting: those live in a vault's settings files and are per vault, while a client serves every account on the machine.
- An MCP server: a lifecycle and handshake to deliver JSON a command already returns.
- A Google loopback server and `holi-google` script of its own: the core bridge already authenticates per vault and supplies the remote.
- Plain-text mail: a mail reader must render mail.
- Encrypting the cache: needs a native module and forecloses FTS5.
- Per-vault cache or wipe-on-switch: mail is account data, and wiping refetches on every switch.
- Calendar `syncToken`: incompatible with `timeMin`/`timeMax`.
- Parsing join links from the `.ics`: a second, drifting source of truth.
- `labels.get` for tab counts: counts archived mail.
- A refcounted single disconnect: one button with hidden meanings.
- Rich-text composing or a local draft store: a second model, a second home.
- Withholding `send`, or `permissions.ask` alone for it.
- A single fence around a command's whole output: `--json` would stop being JSON, and a field read out of a spilled file would carry no marker.
- Fencing only mail from other people: Holi cannot tell which text in a thread or an event is the person's own.

## Code

- The `google` plugin, on by default (nothing shows until an account is connected on this machine): `apps/desktop/src/plugins/google/`.
- `main/`: `index.ts` (activation: the accounts manager, each account's cache, the capabilities), `untrusted.ts` (what the CLI door fences), `passthrough.ts` (`holi google api`'s rule table and its answer's fence), auth (`loopback-flow`, `pkce`, `credentials`, `session`, `accounts`, `vault-accounts`, `token-store`, `electron`, loaded only at activation), data (`gmail`, `mail-sync`, `cache`, `data`, `calendar`, `invite`, `people`, `mime`), `capabilities` (every door) and `seed.ts` with `vault/shipped/.claude/hooks/google-send-gate.mjs` and `skills/gmail-calendar/`, plus the gate's hook entries and ask rules.
- `renderer/`: the `mail` and `agenda` surfaces and their nav items (shown once an account is connected, `account.ts`, whose atoms follow the open vault and a refresh nonce), the Connections settings section, the compose dialog (opened as the plugin dialog), `mail-html.ts` and `mail-frame.ts`. Making a task from a thread or event types only the `tasks.create` slice it calls (`tasks.ts`) and shows only while `useHasCapability('tasks.create')`; Summarize hands the agent a prompt through the agent service (`useAgentService`), and shows only while there is one.
