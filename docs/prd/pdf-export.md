# PRD — PDF export: branded syv.ai documents

> **Built and live.** Convert-to-PDF is in the app (`features/pdf/ConvertToPdf.tsx`, `main/pdf/*`), templates are vault content under `.holi/document-templates/` (D66), the agent has the same capability through the seeded `md-to-pdf` skill, and since 2026-09-21 the output opens in a tab (`features/files/PdfViewer.tsx`, §Viewing a PDF). This was written as a phase-2 stub, pulled forward by D62, and then left describing a future it had already become — including a line saying this would be *"an agent skill, not an in-app export UI"*, which stopped being true when the export UI shipped.

## Summary
Turn any Holi markdown doc into a **branded syv.ai document** by rendering it through a **Typst template** — producing a company-styled PDF (and/or Typst source). This is the "make it presentable / send it to a client" step a real company DMS needs: notes and drafts live in Holi, finished documents come out looking like Syv.

## Why Typst
- Typst is a modern, fast, scriptable typesetting system (LaTeX-class output, far simpler authoring) with a clean programmatic API — a good fit for template-driven, branded document generation from markdown.
- OSS, self-hostable rendering (aligns with the stack's self-hosted, OSS, no-vendor-lock-in stance).

## Goals — as built
- **Markdown is the source and stays the source.** Author in Holi, emit a branded PDF; nothing round-trips back. This is D62 restated: the vault is text-first *by authorship*, and a PDF is an output the vault emits rather than a document it holds.
- **Templates are committed vault content**, under `.holi/document-templates/<slug>/` — a `template.json` plus `template.typ` plus `assets/`. The path is named for its *purpose*, not its mechanism (D66): in a notes app, a bare `templates/` invites "templates for *notes*?". `main/pdf/templates.ts` holds the single source for that path, and the seed content lives internally under `main/agent/templates/`, which is build content rather than the vault convention and is deliberately not renamed to match.
- **A team exports consistently because the template is in the repo.** Nobody installs a brand.
- **Typed template fields.** `template.json` declares the metadata a template consumes, and the export UI renders a widget per field rather than a free-text blob — so a template can require a recipient and get one. Frontmatter prefills them, because the document usually already knows its own title.
- **Two front doors, one pipeline.** The Convert-to-PDF UI and the agent's `md-to-pdf` skill both shell out to the same renderer. The skill is what makes *"export this as a proposal"* work in a sentence; the UI is what makes it work without one.
- **Typst is resolved, not assumed.** `TYPST_BIN` override → a version-pinned cached download under `userData/typst` → `PATH`. Pinned to one version (`TYPST_VERSION`) because templates are authored against it, and a template that renders differently on two machines defeats the point of committing it.
- **Wiki-links and images resolve at conversion**, so a document full of `[[links]]` exports as prose rather than as syntax.

## Non-goals
- **A WYSIWYG document designer.** Templates are code, authored once and chosen by users — the standing "users are developers, so prefer a documented schema over a builder" rule.
- **Round-tripping Typst back into markdown.** The PDF is an artifact; the markdown is the document.
- **Any output target other than PDF** — the `.typ` source, or a Google Docs export. Asked once during design and **nobody has asked since**; it should not be built until someone does.

**Six templates ship** (2026-08-04): `plain`, plus `letter`, `memo`, `report`, `proposal` and `contract` — the original ask, and then some — over a shared `_brand/` foundation (`brand.typ`, `figures.typ`, the logo and the fonts) that carries the house look so a template file is about *its* document and nothing else. Design of record: [`../specs/2026-08-04-document-template-set-design.md`](../specs/2026-08-04-document-template-set-design.md). **This was also the first real test of the field schema**, which until then had exactly one consumer; five `template.json` manifests now exercise it, and it needed no widening to take them.

**What is not built** — distributing a template set across vaults — is in [`../not-built.md`](../not-built.md).

## Resolved, and worth not re-litigating
- **Where rendering runs** → locally, against a resolved-and-pinned Typst binary. The original recommendation was a server-side Typst service for font and asset consistency; there is no server (D60), and pinning the version plus committing the assets into the vault buys the same consistency without one.
- **Whether this is a skill or a UI** → both, over one pipeline. It was specified as a skill *instead of* a UI, and that was wrong: the agent route needs no dialog and the human route needs no sentence.

## Viewing a PDF

**A `.pdf` in the vault opens in a tab** (D103, 2026-09-21), and the first thing it has to do is render this document's outputs exactly: the seven templates, the brand fonts, the logo. It does, through [embedpdf](https://www.embedpdf.com) in its ready-made shape, `@embedpdf/react-pdf-viewer` 2.15.1 over a PDFium build compiled to WebAssembly. MIT, with PDFium's BSD-3 licence alongside; the wasm ships in the package and Vite emits it as an app asset, so the viewer works offline and makes no network request at all. That takes three settings, not one: the library's CDN font fallback is off (`fontFallback: null`); its own fonts are not fetched from Google Fonts (`fonts`), its UI in Holi's `--font-sans` and the four typed-signature faces (Caveat, Dancing Script, Great Vibes, Pacifico, OFL-1.1) bundled with the app as `@fontsource` packages and loaded when the signature panel opens; and the stamp plugin's default manifest on jsDelivr is dropped (`stamp.manifests: []`). The last two were found on 2026-09-23 by watching the network during a real session: the D103 evaluation had not seen them, because they are requested when the viewer starts and when the signature dialog opens. Read-only viewing is scroll, zoom, page navigation, text selection and search inside the document; the toolbar's Annotate and Shapes tabs add highlight, underline, strikeout, squiggly, ink, shapes, free text and sticky notes. Nothing couples the viewer to the templates beyond rendering what they produce, and there is no live preview beside a note.

- **Bytes cross the IPC seam, not the asset protocol.** `files.read` returns the file as a `Uint8Array` that structured clone carries verbatim, and the renderer wraps it in a blob URL the viewer fetches same-origin. `holi-vault://` serves the same bytes to `<img>`, but a renderer `fetch` of it fails on CORS, and the one-line header that would fix it was rejected: it would open the protocol to the sandboxed vault-app frames too, because a packaged `file://` renderer sends the same `null` origin those frames do, and D74's claim that an app cannot fetch `holi-vault://` rests on exactly that absence.
- **A mark is saved into the file.** With embedpdf's `autoCommit` a highlight is committed into the in-memory document as it is drawn; a quiet second after the last annotation event the export plugin renders the whole document to bytes and `files.write` puts them back at the same path, atomically, returning the mtime. The PDF then syncs like any binary: autosave commits it, git carries it, Preview and every other reader see the marks. A mark or comment is signed with the signed-in GitHub `login` (the annotation's `/T`), not the library's default "Guest", so other readers see who made it. The cost is stated rather than hidden: every mark rewrites the whole file, and the diff is opaque.

- **Signatures (D104).** A Signatures button on the top bar, beside Search and Comment, opens the viewer's signature panel (the viewer keeps it in an Insert tab, which is gone: it would only have repeated the button); Create New Signature, a round plus beside the panel's title (the viewer's own button, reshaped in the shadow root), takes a drawn, typed or uploaded signature, and placing one on a page is an annotation like any other, saved into the file. Signature only, with no initials: in the library's default mode Save stayed disabled until both were filled, with nothing saying so. **The signatures you make are kept in `userData`**, never a vault (`pdf-signatures.json`, through `pdf.signatures` and `pdf.saveSignatures`): the viewer holds them in memory, and a vault is a shared repo. One list per machine and person, in the library's serialized form, loaded by each viewer as it opens and saved on every change; two viewers open at once each save their own list, so the later change wins. The dialog is Holi's `--popover` surface, and its three signing areas are paper, white in dark mode and `--muted` in light, because a signature is black ink. **The panel says what placing one shares**: at its foot, for as long as it is open, a note that a placed signature is saved into the PDF, which is committed to the vault, that anyone with access can copy it, and that removing it later leaves it in the history. It is a Holi element portalled into the viewer's shadow root, styled there from tokens.

- **Read-only marks (D105).** Beside Signatures, a lock on the top bar makes every mark, comment and signature read-only: it sets the PDF `readOnly` annotation flag, which the viewer honours by making the annotation unselectable (it cannot be moved, edited or deleted) and other readers honour too, and the file is saved like any mark. Once every mark is read-only the button becomes "Make marks editable" and clears the flag again. Anyone may do either; a mark added later stays editable until the next toggle; links, form fields and comment popups are left alone. The flags are the whole state, read from the viewer's store, so there is nothing to keep in sync. It guards against accidental edits, not against a collaborator: another PDF tool clears the flags, and git can restore the file from before. Rejected: a sidecar JSON beside the PDF (the original never changes, but only Holi shows the marks), in-memory marks, and shipping read-only first.
- **The file on disk stays the truth.** The viewer remembers the mtime its write produced, so the snapshot tick that write causes is not a reload; a snapshot with any other mtime is a re-export from Convert-to-PDF or a pull, and the bytes are fetched again. A reload is skipped while a save is pending, so at most one quiet second of marks is ever at risk.
- **The chrome is themed, not replaced.** The viewer's UI is Preact inside a shadow root, but its palette is a token map, and a value of `var(--background)` crosses the shadow boundary and resolves against the vault's theme (D64). `lib/pdf-viewer-config.ts` maps Holi's whitelisted tokens onto that palette; a node test refuses a colour literal there. The toolbars, the Annotate/Shapes bar and the sidebars all paint from `--background`, the pane's own colour, so the viewer's chrome is as flat as Holi's. It draws no rules either: toolbar and sidebar edges, section rules, the dividers between toolbar groups and the outline of menus and the page pill are cleared by CSS in the shadow root (menus keep their shadow, as Holi's do), and only form controls keep an outline, dimmed to `--divider` and brightened to the accent while focused. A toolbar button shows selected (the pointer, pan) or hovered by its background alone, with none of the ring or shadow the library draws, and a sidebar (thumbnails, signatures, search, comments) lies flat on the pane, `--background` with nothing between them, as Holi's own file tree does, with no edge, ring or shadow inside it but a form field's dimmed edge (a menu floating over it keeps its shadow); a selected comment is marked by `--accent`, the comments panel is 360px wide where the others keep the viewer's 250px (a `width` in its UI schema, merged like the toolbar), its comment field is a textarea that wraps and grows with its text (Holi's, portalled in beside the viewer's one-line input, which it feeds: every change is written into that input and Enter clicks the viewer's own send button, so whether it is a first comment or a reply stays the library's decision; a line break becomes a space, since the input and the comment display both drop it), and a comment or reply leads with its author's name, with none of the round icons and initials the library draws beside it. A sidebar arrives from the side it docks on (D98's arrive, the app's own slide and fade, in its motion tokens): thumbnails and signatures from the left, search and comments from the right. It leaves at once, because the viewer unmounts a closing sidebar in the same render and its sidebar component is not replaceable. Its tooltip is Holi's popover surface and its scrollbar is Holi's (10px, a clear track, a thumb shown on hover), redrawn inside the shadow root because the app's global scrollbar rule does not reach it. The only colours still the library's own are its overlay and its warning, success and info states, which Holi has no token for. A mode flip goes through the viewer's `setTheme`, not a remount, so it does not reload the document. The one colour outside the palette is the page before PDFium paints it, which the library hard-codes white inline: on a dark PDF that was a white flash on open. A `<style>` in the viewer's shadow root paints that placeholder `--muted` instead; the rendered page brings its own white paper, so a white PDF still looks white. The viewer also **arrives once, whole**: left to itself it shows an engine spinner, then "Initializing plugins…", then its toolbar, then the pages, over some 300 ms. It is laid out invisible and fades in (D98's arrive, `motion-in-fade`) when the first page image loads, with a 1.5 s fallback so a broken file's error or a password prompt is never left invisible. **A PDF opens at 150%, or at fit-width when the page would overflow the pane at 150%** (100% is one CSS pixel per PDF point). The viewer has no such mode, so it opens at fit-width and the first zoom each document gets is capped, before the first page paints; choosing Fit Width later from the menu still fits the width. **Opening a PDF focuses it**, as opening a note focuses its editor, and a click anywhere in the viewer does too, so its own keys work where it has focus and nowhere else: **⌘F opens the viewer's search panel with the caret in its field**, Escape in the field or ⌘F from the viewer closes it again, and focus returns to the viewer rather than falling out of it. A reload after a foreign change does not take focus back. The page scroller reserves its scrollbar gutter from the start, so fit-width is not recomputed when the scrollbar appears.
- **Its keys stay its own, and reach it only from itself.** ⌘F, ⌘= and ⌘-, ⌘0 and ⌘1, the arrows, `h` and `p`, ⌘Z are document-scoped like the mail view's ⌘F and do not join the commands table ([`command-palette.md`](command-palette.md)). The commands plugin binds them on `document` and would take `h` or an arrow from the file tree, so `PdfDocument` registers a guard in a layout effect, which React runs before any child's effect, that stops a key the viewer would claim when the event did not start inside the viewer. What would collide with Holi is disabled by category, which removes the command and its shortcut together: `document-open` (⌘O is a file picker), `document-print` (⌘P is the palette), `document-close` (⌘W is a menu accelerator and the tab is Holi's), `capture` (⌘⇧S), and with them the things a pane is not for: export, protect, fullscreen, the hamburger menu they hang from, redaction, stamps, forms, and the Insert tab's rubber stamp, image and attachment. The names are the viewer's own (`insert-rubber-stamp`, not `stamp`), and a name that matches nothing fails silently, which is how signatures leaked in before D104 made them a feature. A disabled command is not claimed by the guard either, so ⌘P opens the palette with a PDF focused.
- **The viewer is a lazy chunk.** `PdfViewer` is `React.lazy` around the module that imports embedpdf, so the renderer's main chunk stays where it was and the 4.6 MB wasm and 0.7 MB worker load on the first PDF.

**Rejected: the headless route.** embedpdf's core plus plugins with a toolbar built from Holi's primitives gives full control of the chrome, and it is the shape the old Holi built: 1550 lines, a worker engine that hung on "Loading PDF…" because a root-relative wasm URL does not resolve against a `blob:` worker base, and StrictMode double-mount races. The ready-made toolbar covers the whole scope; the chrome is themed instead. **Not chosen either:** any other library. Nothing disqualified embedpdf, and the evaluation was not asked to compare.
